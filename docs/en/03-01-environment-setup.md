# 3.1 Environment Setup

## 3.1.1 Leaderboard

Note: As of 2026-05-22, the environment-setup direction does not appear to have a mature, continuously updated public leaderboard with centralized submissions comparable to BFCL, Terminal-Bench 2.0, or SkillsBench.

## 3.1.2 Bench

- [SUPER](https://arxiv.org/abs/2409.07440): Evaluates setup completion and task execution in real ML/NLP research repositories. Core idea: split research reproduction into Expert, Masked, and AutoGen task groups, while recording both success rate and process progress, exposing practical agent failures in dependency installation, script-entry discovery, and experiment execution. ([open-source code](https://github.com/allenai/super-benchmark), [dataset](https://huggingface.co/datasets/allenai/super))
- [Repo2Run](https://arxiv.org/abs/2502.13681) (public benchmark + agent): Evaluates automatic construction of executable Docker environments and passing unit tests for given code repositories. Core idea: model environment construction as a closed-loop synthesis problem of `build image -> run tests -> read feedback -> fix Dockerfile`, and release an evaluation set containing 420 Python repositories, according to the paper.
- [RepoST](https://arxiv.org/abs/2503.07358): Evaluates executable sandbox testing environment construction for repo-level code generation. Core idea: isolate target functions and local dependencies to generate standalone test scripts, reducing the cost of full-repository dependency configuration, and release RepoST-Train / RepoST-Eval to support training and evaluation with execution feedback. ([project page](https://repost-code-gen.github.io/), [open-source code](https://github.com/yiqingxyq/RepoST))
- [EnvBench](https://arxiv.org/abs/2503.14443) (public benchmark; [open-source code](https://github.com/JetBrains-Research/EnvBench), [data and trajectories](https://jb.gg/envbench)): Evaluates repository-level environment configuration for Python and JVM (Java/Kotlin), emphasizing real configuration challenges rather than one-click install scripts. Core idea: build a scalable setup-eval system with automatic metrics such as static analysis for Python missing imports and compilation checks for JVM, and release reproducible experiment trajectories according to the paper/official resources.
- [PIPer-eval](https://huggingface.co/datasets/PIPer-iclr/PIPer-eval): Evaluates Python environment installation planning and repair ability. Core idea: organize dependency installation, conflict diagnosis, and execution feedback into a public evaluation-results dataset, suitable as a setup-planning reference beyond EnvBench/Repo2Run.
- [CompileAgentBench](https://arxiv.org/abs/2505.04254) (public benchmark + agent; [open-source code](https://github.com/Ch3nYe/AutoCompiler)): Evaluates compile-error localization and repair in real repositories/projects. Core idea: chain dependency installation, build commands, compile-log parsing, and patch writeback into an executable loop, directly measuring agents' ability to move projects from uncompilable to compilable.
- [SetupBench](https://arxiv.org/abs/2507.09063) (public benchmark): Evaluates bootstrapping development environments from a bare Linux sandbox across multiple language ecosystems, databases, and multi-service orchestration. Core idea: use "deterministic success commands" as acceptance criteria, isolating environment bootstrap as a key sub-capability and analyzing systematic agent failures in exploration efficiency and persistent modifications.
- [BuildBench](https://arxiv.org/abs/2509.25248): Evaluates compile and build success rates for real open-source software. Core idea: place agents under complex build systems, dependency chains, and system-package constraints, testing whether they can read logs, fix configuration, and ultimately complete verifiable builds. (Note: at the time of writing, no stable official standalone open-source repository/data entry has been seen.)
- [EnConda-bench](https://arxiv.org/abs/2510.25694): Evaluates planning, error diagnosis, feedback repair, and final execution ability during environment configuration. Core idea: construct Docker-verified tasks by injecting realistic README errors, measuring both end-to-end executability and trajectory-level internal abilities. ([open-source code](https://github.com/TencentYoutuResearch/EnConda-Bench))
- [Multi-Docker-Eval](https://arxiv.org/abs/2512.06915): Evaluates executability and "failure-to-success" repair ability for Docker environment build/repair agents. Core idea: use metrics such as Fail-to-Pass and Commit Rate to measure end-to-end repair quality from build failure to runnable environment. (Note: at the time of writing, no stable official standalone open-source repository/data entry has been seen.)
- [DevOps-Gym](https://arxiv.org/abs/2601.12961): Evaluates build configuration, deployment, testing, and operations tasks in DevOps scenarios. Core idea: use executable CI/CD and repository-operations tasks to test whether agents have engineering-operation ability across toolchains and services. ([project page](https://www.devops-gym.com/), [open-source code](https://github.com/ucsb-mlsec/DevOps-Gym))
- [MEnvBench](https://arxiv.org/abs/2601.22859) (public benchmark): Evaluates environment construction and verifiable execution for polyglot repositories. Core idea: split environment construction into a Planning-Execution-Verification loop and use environment reuse to reduce build overhead; the paper reports 1000 tasks, 10 languages, and 200 repositories, subject to the paper.
- [ResearchEnvBench](https://arxiv.org/abs/2603.06739): Evaluates environment synthesis for research-code execution. Core idea: given a research repository, documentation, and target execution setting, require agents to actually set up the environment and run the runtime successfully.

## 3.1.3 Agent Harness

- [Installamatic](https://arxiv.org/abs/2412.06294) ([open-source code](https://github.com/coinse/installamatic)) is the most typical agent for installation-step synthesis and failure recovery.
- [ExecutionAgent](https://arxiv.org/abs/2412.10133) ([open-source code](https://github.com/sola-st/ExecutionAgent)) represents "fixing environment commands based on execution feedback."
- [Repo2Run](https://arxiv.org/abs/2502.13681) ([open-source code](https://github.com/bytedance/Repo2Run)) explicitly casts environment construction as Dockerfile synthesis plus a testing loop.
- [SetUpAgent](https://arxiv.org/abs/2503.07701) (open-source code: not released) focuses on self-reflective Dockerfile synthesis and environment patching, representative of explicitly agentizing "trial-and-error environment setup."
- [SWE-smith](https://arxiv.org/abs/2504.21798) ([open-source code](https://github.com/SWE-bench/SWE-smith)) connects executable environment construction, task synthesis, and verification pipelines, closer to a "data factory driven by environment-setup ability."
- [CompileAgent](https://arxiv.org/abs/2505.04254) ([open-source code](https://github.com/Ch3nYe/AutoCompiler)) targets compile-failure repair, emphasizing localization of missing dependencies, API incompatibilities, and build-script issues from compiler logs.
- [SWE-Builder (SWE-Factory)](https://arxiv.org/abs/2506.10954) ([open-source code](https://github.com/DeepSoftwareAnalytics/swe-factory)) modularizes environment construction into reusable components for large-scale generation of executable SWE training and evaluation instances.
- [OSS-BUILD-AGENT](https://arxiv.org/abs/2509.25248) (open-source code: no stable public repository found) focuses on recovering build failures in real open-source software, repeatedly modifying dependencies, configuration, and scripts based on build logs until compilation succeeds.
- [GradleFixer (Automating Android Build Repair)](https://arxiv.org/abs/2510.08640) (open-source code: not released) is boundary-related: it focuses on Android/Gradle build-failure repair, with tasks strongly dependent on build and dependency-environment operations; its ideas are relevant to "environment setup + build repair" tasks, but it is not a general Repo2Run/EnvBench-style benchmark.
- [SWE-Bench++](https://arxiv.org/abs/2512.17419) ([open-source code](https://github.com/TuringEnterprises/SWE-Bench-plus-plus)) explicitly introduces environment synthesis into an automatic SWE benchmark generation pipeline and compares against setup agents.
- [MEnvAgent](https://arxiv.org/abs/2601.22859) ([open-source code](https://github.com/ernie-research/MEnvAgent)) turns "polyglot environment construction" into a multi-agent Planning-Execution-Verification loop and introduces environment reuse.
- [DockSmith](https://arxiv.org/abs/2602.00592) (open-source code: not released) treats Docker environment construction as a core agentic ability for training/evaluation, using Multi-Docker-Eval as its main evaluation benchmark.
- [SWE-Universe](https://arxiv.org/abs/2602.02361) (open-source code: not released) advocates large-scale automatic construction of verifiable SWE environments and task data, with environment ability evaluated on the authors' own multilingual task set.
- [HerAgent](https://arxiv.org/abs/2602.07871) ([open-source code](https://github.com/EuniAI/HerAgent)) focuses on automatic environment deployment and performs unified comparative evaluation on multiple setup-related sub-benchmarks; see the paper.
- [ScaleSWE](https://arxiv.org/abs/2602.09892) ([open-source code](https://github.com/AweAI-Team/ScaleSWE)) constructs large-scale verified SWE instances through a multi-agent pipeline of setup agent, test creation agent, and problem synthesis agent.
- [SWE-rebench V2](https://arxiv.org/abs/2602.23866) ([open-source code](https://github.com/SWE-rebench/SWE-rebench-V2)) releases an interactive setup synthesis agent and image build flow for complex repository setup automation.
- [SWE-Hub](https://arxiv.org/abs/2603.00575) ([open-source code](https://github.com/zhenglw02/SWE-Hub)) introduces Env Agent as the execution substrate for a data factory, emphasizing environment setup as infrastructure in large-scale SWE pipelines.
- [RepoLaunch](https://arxiv.org/abs/2603.05026) ([open-source code](https://github.com/microsoft/RepoLaunch)) abstracts cross-language repository build-test execution into a general pipeline.
- [daVinci-Env (OpenSWE)](https://arxiv.org/abs/2603.13023) ([open-source code](https://github.com/GAIR-NLP/OpenSWE)) uses a multi-agent pipeline to synthesize executable Docker environments and evaluation scripts at scale, leaning toward "reproducible infrastructure + environment synthesis."
- [BootstrapAgent](https://arxiv.org/abs/2605.15815) ([open-source code](https://github.com/Vossera/BootstrapAgent)) distills repository-startup experience into a reusable `.bootstrap` contract; its core flow includes evidence extraction, structured planning, Docker verification, trace-driven repair, and clean replay, aiming to reduce repeated trial and error for later coding agents.

## 3.1.4 Skill

- [docker-configuration-validator](https://skills.sh/rknall/claude-skills/docker-configuration-validator) is suitable for first checking Dockerfile / compose configuration.
- [docker-containerization](https://skills.sh/ailabs-393/ai-labs-claude-skills/docker-containerization) is suitable for quick containerization.
- [devcontainer-helper](https://skills.sh/gabeosx/agent-skills/devcontainer-helper) is suitable for standardizing local development environments.
- [package-managing](https://skills.sh/ingpdw/pdw-python-dev-tool/package-managing) is suitable for dependency installation and version governance.
- [error-recovery](https://skills.sh/zpankz/mcp-skillset/error-recovery) is suitable for repair loops after environment startup fails.
- [multi-stage-dockerfile](https://skills.sh/github/awesome-copilot/multi-stage-dockerfile) is suitable for generating reproducible and trim multi-stage Dockerfiles, mitigating large images, unstable dependencies, and slow builds.
- [devcontainer-setup](https://skills.sh/shipshitdev/library/devcontainer-setup) is suitable for solidifying repository environments into reusable devcontainer configuration, with emphasis on monorepo mounting and port mapping.
- [devcontainer-setup](https://skills.sh/trailofbits/skills/devcontainer-setup) is suitable for packaging multilingual toolchains together with Claude Code into a devcontainer, with emphasis on safety and engineering.
- [python-dependency-resolver](https://skills.sh/jorgealves/agent_skills/python-dependency-resolver) is suitable for locating pip version conflicts, circular dependencies, and inconsistent constraints.
- [install-script-generator](https://skills.sh/luongnv89/skills/install-script-generator) is suitable for generating one-command cross-platform installation scripts.
- [repo-runner](https://clawhub.ai/zyl-hub/repo-runner) is suitable for starting projects according to repository documentation with risk guardrails, closer to a runbook/execution assistant.
