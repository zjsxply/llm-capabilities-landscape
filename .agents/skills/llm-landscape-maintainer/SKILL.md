# LLM Landscape Maintainer

## Capability Modes

- **Seed expansion**: start from user-provided seed papers, projects, benchmarks, or agents; expand through surveys, baselines, references, citations, repositories, leaderboards, and implementation checks before updating the landscape.
- **Model-card alignment**: compare the latest vendor model cards/system cards against the repository inventory, identify benchmark/task gaps, classify them into the taxonomy, and add important public or closed/internal evaluations with clear public-status notes. For this workflow, read `references/model-card-gap-workflow.md`.
- **Venue-track intake**: when the user asks for the latest papers from a conference, proceedings, workshop, or named track, enumerate the official accepted-paper source first, then screen and expand the accepted set through papers, repositories, and citation edges. Keyword search and citation closure are supplements, not completeness checks for a recent venue.
- **Parallel intake with subagents**: when a venue or citation-closure task is split across subagents, assign disjoint scopes and require each subagent to write both a screening report and a short lessons-learned memo under `.tmp/`. The parent agent keeps final edits single-writer, then folds durable lessons back into this skill.

## High-Value Workflows

- **Taxonomy split or category cleanup**: define the task axis first, add paired English/Chinese category files when needed, update both README files, verify the destination heading in both language files before deleting any source entry, merge independent import headings into the normal chronological section, then run `rg` for every moved benchmark name across `docs/en` and `docs/zh` to catch leftover mentions in Bench and Agent Harness prose.
- **Latest-conference intake**: pin the venue, year, track, and acceptance status; enumerate its official index, proceedings, or OpenReview venue page/API; save a screening ledger in `.tmp/` with official title, alias, paper URL, repository/dataset URL, inclusion decision, and destination file; only then run taxonomy filtering and citation expansion. For NeurIPS Datasets and Benchmarks, explicitly query the Datasets and Benchmarks track rather than assuming a general NeurIPS or arXiv keyword search covers it.
- **Recent top-venue Model/Survey/Harness sweep**: when the user asks for recent top-venue coverage, search the official venue population before topic search. For OpenReview venues, record `content.venueid`, `venue`, `forum`, `title`, `abstract`, `link_to_code`, and `pdf`; for ACL-family venues, prefer volume `.bib` files or ACL Anthology stable pages over event HTML; for ICML, cross-check PMLR proceedings because PMLR title pages can expose papers that keyword scans over OpenReview metadata under-rank. Keep `add`, `provenance-only`, `sync/move`, and `defer` states separate so already-included arXiv entries are not duplicated only because a venue version appeared.
- **Subagent lesson loop**: after any multi-agent intake, ask each subagent for a concise memo covering its source scope, missed-recall patterns, title or alias drift, classification conflicts, duplicate handling, and concrete skill-rule suggestions. Save the memos in `.tmp/<task>/subagent-lessons/`, review them before the final user summary, and update this skill when they reveal reusable process changes.
- **Repository hygiene after long runs**: inspect both the current working tree and the complete tracked `HEAD` tree, because a user may commit important work before requesting cleanup. Check tracked paths for empty files, caches, generated outputs, batch/chunk names, large or binary artifacts, exact duplicates, broken symlinks, and misplaced files; separately check ignored and untracked paths outside `.tmp/`, `.cache/`, and `.venv/`. Keep reusable parameterized utilities under this skill, but move scripts that hard-code paper identifiers, one-round decisions, fixed titles, or dated override tables to `.tmp/<task>/`; lack of documentation alone is not deletion evidence. Never rewrite, amend, or revert the user's commit during this cleanup: preserve one-off artifacts under `.tmp/` when useful and expose tracked removals as an ordinary working-tree diff.
- **Model-card gap ingestion**: extract vendor-reported evaluations into a table, normalize aliases against the recursive `docs/en/` tree, classify by task axis, add closed/internal suites only with explicit "not publicly released" wording, and place them by card/report date.
- **Survey-section intake**: cached citation and reference candidates are only a noisy starting point for surveys. For each task page, define the category boundary first, then run a capability-specific enrichment pass over recent arXiv, proceedings, publisher pages, and web sources using aliases for the task, "survey", "review", "position", "tutorial", "benchmark survey", and domain-specific terms. Prefer the last one to two years, include older papers only when they are high-impact or still field-defining, and classify candidates as direct, adjacent, domain-specific, foundational, or reject/noise before editing.
- **Survey cleanup and category QA**: when replacing placeholder survey prose, do not treat the active file as proof of the right category. For every touched entry, reread the title, abstract, and neighboring sections, then confirm whether the work belongs in `Survey`, `Model`, `Agent Harness`, or a different topic before polishing the sentence. If an item is moved, remove the old primary listing and validate both source and destination pairs.
- **Generic TLDR cleanup**: when a user flags vague entries, first audit the recursive split-tree docs with `generic_tldr_audit.py`, then rewrite each touched bullet from the paper abstract, official project page, repository README, or publisher metadata. A valid TLDR must state the paper's distinctive mechanism, artifact, evaluation protocol, or contrast with nearby work; title repetition and category-template phrases are not acceptable. Treat cleanup as taxonomy QA: if the abstract shows the item is a `Model`, `Bench`, `Survey`, off-axis project, or only adjacent infrastructure, record the move or rejection instead of polishing the wrong section. If harness cleanup relocates entries into `Model` or `Bench`, audit those destination files in the same pass; otherwise generic model-side prose can merely be moved rather than fixed. In audit triage, use the EN/ZH pair summary to assign whole paired files, and separate semantic template matches from format-only title repetitions so cleanup priority reflects evidence quality rather than Markdown duplication noise. Keep placeholder regex families section-scoped; model, bench, survey, agent-harness, and skill templates should not fire in introduction or methodology pages unless those pages use the same section filename.
- **Parent-approved closure discipline**: a `decision == include` row from subagent or parent-review JSON is still only a recommendation unless the official docs already contain it or the parent has reread evidence and written a concrete TLDR. For large closure batches, first build a final-decision ledger over every include row with `already_in_docs`, `duplicate`, `included`, `rejected_offaxis`, `rejected_route_elsewhere`, `rejected_insufficient_evidence`, or `rejected_unverified_template_candidate`. Treat `checking`, `deferred`, and `evidence_insufficient` as temporary queue states only; before closeout, resolve every row to final `included` or `rejected` with a concrete reason. Do not bulk-apply generated bullets that say only "contributes a model-side method", "adds an agent workflow", "surveys methods", or title-derived equivalents. If a batch is mostly template bullets, it is valid to mark those rows rejected/unverified in the ledger rather than polluting docs; important items should be reseeded or reread individually with abstracts.
- **Manual template scan after zero audit**: a zero result from `generic_tldr_audit.py` is not enough for closeout. Always run a targeted `rg` over touched files for newly observed phrase families such as `Agent Harness candidate`, `Adds a agent harness`, `Contributes an agent workflow`, `Candidate 3.2.3`, Chinese `类型：agent harness/可复用执行框架`, `核心价值：为 ... 补充`, `适合补充 research Agent Harness`, and any user-flagged wording. If manual scan finds matches, either rewrite from evidence or remove/reroute off-axis entries, then rerun URL parity and chronology checks.
- **Survey placeholder recall**: do not trust a zero-match survey audit until a manual phrase scan also checks families such as `Surveys recent methods, risks, and open problems for ...`, `Surveys ... capability, adding a recent map ...`, `Adds a survey reference for ...`, `Survey candidate for parent review`, Chinese `梳理科研相关方法、风险与开放问题`, `综述研究型智能体或自动发现能力`, `补充科研的 Survey 条目`, `梳理、分类或定位该能力方向`, and `后续父级复核`. When found, add section-scoped regexes to `generic_tldr_audit.py`, rerun the targeted pair, and rewrite from abstracts rather than title cues.
- **Parallel generic TLDR closeout**: assign at most one writer per EN/ZH file pair. A worker should either rewrite both languages in the same bounded batch or write only `.tmp/` evidence notes; do not leave English-only official edits without an immediate Chinese sync pass. URL-set equality is necessary but not sufficient for bilingual quality: after any partial rewrite, run `bilingual_tldr_sync_audit.py` or manually compare changed URL rows to catch "English concrete, Chinese still template" drift. Closeout reports must state official files edited, exact counts, remaining generic-audit counts, URL-check result, `git diff --check` result, and whether any phase is only evidence gathering. If a worker applies zero official edits, count it as triage only, not cleanup progress.
- **Changed-row sync reports are queues**: after a high-volume TLDR wave, `bilingual_tldr_sync_audit.py --only-changed-en` can still report thousands of rows because the whole edited file pair remains dirty relative to `HEAD`, not because every newly rewritten row regressed. Interpret this report as the next cleanup queue unless the worker also provides a rewritten-URL residual scan. For quality accounting, combine worker-reported rewritten URL lists, targeted audit before/after counts, URL-set checks, and a small parent spot-check of evidence ledgers.
- **High-volume TLDR dispatch**: for repository-wide placeholder cleanup, run a global `generic_tldr_audit.py` first and dispatch by `Top EN/ZH Pairs By Semantic Match Count`, not by active editor tabs or ad hoc `rg` hits. Use many workers only with disjoint paired-file ownership, bounded rewrite counts, and required self-validation. Prefer 40-120 entries per worker depending on file size; huge `04-model.md` files should be processed in waves so failures or low-quality assumptions are easy to isolate. The parent should keep a live ledger of worker scope, changed files, rewrite/delete counts, remaining audit counts, and any low-confidence caveats before rerunning the global audit.
- **Explicit parallelism requests**: when the user explicitly says to use subagents or accelerate with agents, do not leave the work as a single local cleanup unless the scope is genuinely tiny. Split by EN/ZH file pair or candidate chunk, announce the parent-owned critical-path task, spawn workers with disjoint write ownership, and require each worker to write a `.tmp/` report with evidence sources and validation results. If a worker cannot be resumed or returns no result, record that bounded failure and continue with non-overlapping local work rather than claiming the whole task is complete.
- **Targeted audit fallback**: a global audit report can rank a file pair while its JSON match objects are truncated, omitted by `--max-matches`, or hard to key by paired path. If a worker cannot find its owned pair in the global JSON, it should immediately run a targeted before-audit on the EN/ZH pair and use that residual URL order as the queue, then write both before and after audit files under `.tmp/tldr-current/`.
- **TLDR evidence standard**: do not accept "based on title", "from surrounding context", or "suggested by the title" as a completed cleanup. A worker may use title and local context only for triage or deletion candidates; official prose should be supported by at least the abstract, project page, repository README, publisher metadata, or a clearly inspectable artifact. If a worker reports title/context-only summaries, mark that batch as provisional, rerun a targeted audit or changed-row review, and prioritize those rows for a follow-up reread rather than counting them as fully closed.
- **Template-family expansion during cleanup**: `generic_tldr_audit.py` is a living recall tool, not a proof of absence. If manual `rg` or a worker finds a new repeated phrase family such as `Develops ... with ..., targeting ...`, English `Surveys recent methods...`, English `Adds a survey reference for...`, English `Provides a benchmark, dataset, challenge, or evaluation protocol for ...`, English `Builds an agent workflow or orchestration pattern for ...`, English `Contributes an agent workflow, orchestration pattern, tool loop, memory or control mechanism, or runtime harness for ...`, English `Adds an agentic workflow for generating and optimizing ...`, English `Adds an agent harness entry for ..., focusing on <title>`, Chinese `围绕...构建...面向...`, Chinese `围绕...补充...`, Chinese `提出面向...的...`, Chinese `发布...这一...`, Chinese `为...补充智能体工作流、编排模式、工具循环、记忆或控制机制、运行时框架`, Chinese `重点是《标题》`, Chinese `作为 Model/Bench/Survey/Agent Harness 条目候选`, Chinese `补充一个面向...的...条目，关注...`, Chinese `核心围绕...`, Chinese `综述研究工作流自动化，为后续父级复核...`, or Chinese `梳理、分类或定位该能力方向...` title-restatement prose, add a section-scoped regex to the audit script, rerun the targeted audit, and then dispatch the newly exposed rows. Do not report a file as clean just because the previous regex set returned zero. Keep new regexes narrow enough that concrete mechanism sentences such as a named architecture, memory module, reward, simulator, dataset property, or released dataset description are not treated as generic merely because they use broad verbs such as `构建`, `提出`, or `发布`. A regex match is a review queue, not an automatic rewrite verdict; require the generic construction and its section-specific inventory phrase in the same sentence, and preserve short evidence-backed statements as false positives when appropriate.
- **Generic TLDR migration hygiene**: category moves during placeholder cleanup are not complete until the old category is exact-title searched. After moving or reclassifying an entry, run `rg` for the display name, acronym, arXiv ID, DOI, repository slug, and likely aliases across both `docs/en` and `docs/zh`; remove duplicate primary listings from the source category and keep only deliberate cross-references, then rerun URL, chronology, and bilingual-TLDR audits. For EviSearch-style moves, check both `05-agent-harness.md` and `06-skill.md`, because literature-review agents and their packaged skills often drift together. Route a work to Deep Research only when its final artifact is literature search, evidence extraction, systematic review, survey/report generation, or retrieval-to-synthesis; peer review, rebuttal or author response, experiments, paper production, and paper-promotion artifacts remain in Research.
- **Deep Research versus Research boundary**: route by task artifact, not by the phrase "deep research" in a title. `Deep Research` is narrow: literature search, paper reading, evidence extraction, systematic review, survey/report generation, and retrieval-to-synthesis workflows whose primary product is a literature-grounded report. `Research` is the broader scientific-work category: research planning, hypothesis and idea selection, experiment design/execution, empirical verification, paper production, rebuttal, grant/proposal work, citation repair tools, scholarly source-audit tools, paper-to-code, research visualization, patent/commercialization drafts, math-modeling contest workflows, LaTeX/Overleaf research editors, and end-to-end scientific workflows. Do not put tools such as OneCite, SemanticCite, PaperDebugger, PaperOrchestra skill packs, math-modeling skills, patent-drafting skills, or LMMs-Lab Writer under Writing or Deep Research merely because they manipulate text or citations. Reference moves include `DeepResearch Arena`, `ResearcherBench`, `SimulRAG`, `DEEPSYNTH`, `DDR-Bench`, and `EpiBench`.
- **Research GitHub skill recall**: for Research/Skill intake, do not stop at broad `academic research skill` searches. Split the task into concrete workflow aliases such as `paper figure`, `scientific figure`, `peer review`, `rebuttal`, `humanizer`, `academic setup`, `social science`, `economics writing`, `robustness`, `citation`, `Zotero`, `paper to slides`, `grant`, and `research workflow`; search GitHub, `npx skills find`, `npx clawhub search`, and SkillNet for each family. Add a repository only after README, `SKILL.md`, plugin manifest, install command, or concrete subskill list confirms the behavior. Treat GitHub snippets, search-result descriptions, and marketplace names as candidate signals only. If a general research skill suite contains biomedical, clinical, chemistry, or other narrow vertical subskills, include only the broad reusable research workflow pieces and state the exclusion instead of turning the downstream Research page into a vertical-domain catalog.
- **Research narrow-vertical hygiene**: downstream `Research` is not a catch-all for every paper with a scientific domain label. Remove or reject primary entries whose reusable artifact is tied to one vertical's databases, instruments, simulators, assays, or workflows, such as materials discovery, chemistry/catalysis, biomedical or PubMed systems, climate/weather analysis, soil science, aircraft maintenance, reservoir simulation, PDE or finite-element toolchains, EDA, and similar domain-only applications. Keep a work only when the paper's main artifact transfers beyond the example domain: a general AI-scientist loop, provenance protocol, benchmark design, evaluator, reward/training method, paper-to-code or paper-writing workflow, citation/reproducibility tool, or general scientific workflow infrastructure. Do not keyword-delete a paper just because its abstract uses a narrow case study; `Self-Revising Discovery Systems for Science` is the reference case where the protein-mechanics example supports a broader typed-provenance discovery protocol.
- **Research similarity-first recall**: do not turn cross-disciplinary breadth into a hard gate. During citation closure, compare a candidate's *artifact and workflow* with the existing Research axes before rejecting it: scientific evaluation, experiment design or execution, autonomous discovery, data-science agents, reproducibility, peer review, scholarly integrity, patent and technology transfer, paper figures and presentations, and research software are all in scope. A system instantiated in materials, wireless, causal inference, astronomy, or another non-biomedical field belongs in Research when it makes a concrete contribution to one of those workflows; the domain example alone is not a rejection reason. Reject only when the main artifact is confined to a domain-specific instrument, dataset, simulator, assay, or operational process and offers no transferable research-workflow method. Every rejection must name that actual boundary or the correct destination category; never bulk-apply a generic "not broad/reusable enough" note.
- **Historical rejection repair**: when a classification rule changes, do not re-audit the registry by raw count or re-run every low-signal citation neighbor. Query historical `rejected` records whose notes used an obsolete generic criterion (for example, “too narrow”, “not reusable”, or “not cross-disciplinary”) and whose titles match current Research workflow axes. Enrich the resulting priority queue from cached abstracts or a bounded fresh fetch; classify each as `included`, a specific destination route, a specific Research rejection, or `evidence_insufficient` for a later evidence fetch. Never replace an old generic rejection with another title-only generic rejection.
- **Cross-topic inclusion is not a duplicate**: the checked-paper registry is global, but category coverage is not. A registry record marked `included` in another topic must not suppress a candidate for the current topic when its abstract establishes a second legitimate task role. For example, a STEM benchmark can belong both to `Scientific Knowledge / Bench` and `Research / Bench` when it measures research-agent performance on open-ended scientific work. Candidate generation must compare `record.docs` against the current target pair, not merely exclude every globally checked identifier; retain one canonical paper record while appending both documentation paths.
- **Research cross-topic recall**: periodically run `cross_topic_research_recall.py --arxiv-only` over globally included papers, then review the scholarly-production, research-evaluation, and scientific-workflow queues independently. The script is a high-recall queue, not an inclusion engine: citation generation, generic reproducibility, ordinary software engineering, and title-only "research" mentions are common false positives. Use cached or primary abstracts to decide whether each artifact belongs in broad `Research`, narrowly in `Deep Research`, in its original capability topic only, or outside the landscape; preserve cross-listing provenance in the decision ledger.
- **Survey versus evaluation caution**: a title containing "review", "peer review", or "consistency" is not enough for `Survey`. For example, PiCO is an unsupervised LLM evaluation/ranking method based on peer-review consistency optimization, not a Deep Research survey. If an abstract describes model ranking, evaluator calibration, reward construction, or benchmark scoring rather than a field map, remove it from `02-survey.md` and record the appropriate `Bench`, `Model`, or Benchmark Reliability destination for parent review.
- **Script syntax checks with read-only caches**: if `python -m py_compile` fails because `__pycache__` cannot be written, do not treat that as a syntax failure. Use an AST parse check instead: `python - <<'PY'\nimport ast\nfrom pathlib import Path\nast.parse(Path('SCRIPT.py').read_text())\nprint('syntax ok')\nPY`, then run the script on a narrow smoke target to verify behavior.
- **Low-yield TLDR wave handling**: if a worker inspects a wide 60-100 row window but rewrites only a small fraction, the parent should treat it as partial triage rather than normal cleanup throughput. Require the report to state which audited residuals were false positives, which rows were still unclean, and the exact next residual URL from the after-audit JSON. For the next wave, seed from the after-audit residual list rather than the broad chronological window so workers do not keep circling already concrete or intentionally classification-concern rows.
- **Repeated low-yield file strategy**: if the same file pair has two or more low-yield cleanup waves, stop assigning generic "next N residuals" work. Split the remaining queue by source and decision type instead: arXiv rows with readable abstracts, DOI-only rows needing Crossref or publisher metadata, project/repository rows needing README inspection, and off-axis rows needing parent taxonomy moves. Have workers report counts for each bucket so the parent can decide whether to rewrite, move, or leave bounded residuals.
- **Rate-limited TLDR evidence handling**: when arXiv, publisher, or metadata APIs return `429`, do not fill the remaining rows from titles or surrounding context. Stop the wave at the last evidence-backed row, write the exact next URL and rate-limit source in the report, and leave the residuals for a later pass using cached metadata, slower serial fetches, or alternate official sources.
- **High-volume worker ownership**: never assign a second worker to an EN/ZH file pair until the first worker has reported and the parent has at least checked URL parity and `git diff --check` for that pair. If a high-residual file still needs work, launch a numbered follow-up wave after the prior notes file records the changed rows and remaining patterns. This avoids cross-agent overwrites in very large `04-model.md` files.
- **TLDR spot-check discipline**: URL-set equality is only a structural invariant. For every completed worker wave, spot-check several changed entries by URL against abstracts or official metadata and compare the paired Chinese sentence. If the evidence note says many rows were "obvious from title" or "best effort without abstract", treat that wave as provisional and prioritize those rows in the next audit.
- **Survey-seed intake with subagents**: first verify whether the seed surveys themselves are already present in both languages; if so, use them as provenance instead of duplicating Survey entries. Split subagents by source family or risk axis, require each report to include include/defer/reject rows, bilingual `rg` status, duplicate and alias notes, evidence URL type, and an incomplete-phase statement. The parent then builds separate high-confidence queues for `Bench`, `Model`, `Agent Harness`, and `defer`, rereads current paired docs plus neighboring pages, and applies only parent-approved items.
- **Agent Safety survey intake**: broad Survey sections often already contain recent overviews, so the missing value usually lies in concrete evaluation protocols and runtime systems. Start with `03-bench.md`, `04-model.md`, and `05-agent-harness.md`; check neighboring Memory and Computer Use GUI pages before deciding whether a privacy, memory, or CUA item should be cross-listed. Treat publisher-only or DOI-only survey references as discovery leads until the paper or official artifact is readable enough to support a concise entry.
- **Model-section intake**: model-side work is broader than training papers. Include task-relevant models, pretraining and post-training recipes, model architectures, reinforcement-learning and preference-optimization algorithms, synthetic-data or data-filtering algorithms, world models, reward or verifier models, alignment and guardrail models, inference scaling, and test-time adaptation. Keep pure model-side work in `Model`; keep external orchestration, tool loops, memory, environment control, and multi-agent workflows in `Agent Harness`.
- **Model-vs-Harness misclassification cleanup**: if a user flags a model-side paper in `Agent Harness`, audit neighboring `05-agent-harness.md` files for the same failure pattern before making a one-off fix. Strong Model signals include RL or preference optimization, reward/verifier models, learned controllers, trainable knowledge networks, world models, diffusion policies, neural operators, synthetic training trajectories, data-generation or distillation pipelines, fine-tuning, adapters, and model merging. Move the EN/ZH rows together, then scan moved bullets for stale phrases such as `Agent Harness candidate`, `external workflow`, `parent-routing-needed`, Chinese `适合 ... Agent Harness`, `智能体执行框架候选`, `工作流/工具循环/运行框架`, and rewrite them to name the model-side mechanism.
- **Research Model versus Survey boundary**: research-agent papers that introduce post-trained models, model weights, RL or preference-training loops, reviewer/reward models, synthetic research datasets, or full-cycle research training recipes belong in `Research / Model`, even if they discuss the scientific workflow broadly. `CycleResearcher` is the reference case: CycleResearcher and CycleReviewer plus Review-5k/Research-14k are model-training artifacts, not a survey map.
- **Coding-agent Model intake**: do not stop at SWE-bench agent papers. Search for code-LLM execution-feedback RL, process and outcome reward models, verifiers, unit-test co-training, synthetic edit sequences, diff-by-diff data, formally verified code generation, test-driven SWE data, soft-verified repository trajectories, agent-native mid-training, and vendor coding model technical reports. Use vendor and alias queries for `Codex`, `GPT-*-Codex`, `Claude Code`, `Qwen*-Coder`, `Seed-Coder`, `Kimi-Dev`, `Kimi K2`, `GLM-4.5`, `Devstral`, `Grok Code Fast`, `MiniMax M2`, `Cursor Composer`, and `SWE-*` training papers.
- **Tool-use Model intake**: tool-use training is not exhausted by Toolformer-style API prediction or benchmark pages. Search for synthetic API environments, simulated user-assistant-tool dialogues, executable function-call verification, function-signature graph synthesis, multi-turn function-calling data factories, trajectory distillation, tool selection critics and verifiers, and reinforcement learning in generated tool sandboxes. Use anchor families such as `ToolkenGPT`, `ToolAlpaca`, `GPT4Tools`, `AgentTuning`, `Agent-FLAN`, `APIGen`, `API Pack`, `xLAM`, `Hammer`, `BUTTON`, `MAGNET`, `ToolACE`, `ToolACE-MT`, `FunReason`, `RandomWorld`, `TaskCraft`, `FTRL`, `TARL`, `CodeGym`, `TOUCAN`, `ToolMind`, `AgentScaler`, `GEM`, `EnvScaler`, `EigenData`, `ScaleEnv`, `Agent World Model`, `CM2`, `CoVe`, `COVERT`, `EnvFactory`, `ToolRL`, `ToRL`, and `SimpleTIR`; include vendor technical reports such as `Kimi K2`, `GLM-4.5`, `DeepSeek-V3.2`, and `gpt-oss` when they explicitly describe agentic data synthesis, tool-use post-training, or tool-use RL; place stateful test suites and environment-only releases in `Bench` or `Agent Harness` unless they directly train a model.
- **Long-running Model intake**: include general multi-turn RL, trajectory-level and step-level credit assignment, agent data protocols, process reward models, context folding, self-evolution, test-time memory, plan caching, and belief or memory RL when the contribution is reusable across domains. Keep web-only, GUI-only, SWE-only, or deep-research-only training papers in their topic pages unless they introduce a general agent-training method.
- **Environment Setup boundary**: include work whose central artifact is dependency installation, Dockerfile or image synthesis, build and compile repair, setup verification, repository bootstrapping, or infrastructure-as-code/deployment/drift repair that initializes or restores a *specific runnable target environment*. Exclude generic sandboxing, resource isolation, multi-tenant runtime control, observability, and evaluation substrate papers unless they primarily solve environment bootstrap or build setup; route those to Software Development, Terminal Use, Agent Safety, or Evaluation Methodology according to the evaluated task and reusable artifact. `AgentCgroup` and `SWE-MiniSandbox` are software-development runtime harnesses, not Environment Setup primary entries.
- **Environment Setup artifact-first screen**: the target must be a specified repository, software project, or infrastructure configuration whose runnable state is constructed, repaired, or verified. Before including a candidate, record four evidence fields from the abstract, paper, official project page, or implementation: `target environment`, `setup operation`, `executable verification`, and `failure/recovery loop`. A paper that merely mentions deployment, infrastructure, runtime, cloud, hardware, MLOps, or DevOps is not an Environment Setup fit. The primary output must be an installed dependency graph, Dockerfile/image, build or compile repair, repository bootstrap, IaC configuration, provisioned runtime, or setup-recovery trajectory; otherwise route it to the category matching its actual artifact.
- **Environment Setup section split**: `Survey` admits only surveys or reviews whose organizing subject is environment bootstrap, dependency/build/compile repair, reproducible setup, or setup verification. `Bench` requires a setup/build/compile/bootstrapping task suite or dataset plus an executable acceptance protocol and objective success criteria. `Model` requires a trained or adapted model whose actions or generated artifacts perform environment setup and whose evaluation measures setup success, such as `PIPer` or `DockSmith`; generic LLM serving, inference routing, quantization, KV-cache management, hardware acceleration, or model deployment optimization remains Model in the relevant model/inference topic. `Agent Harness` requires an actual bootstrap/build/verification/recovery loop; generic cloud management, Kubernetes administration, IaC optimization, AIOps, observability, sandboxing, resource isolation, or runtime control does not qualify merely because an agent is used.
- **Environment Setup false-positive postmortem**: prior over-inclusion came from treating broad infrastructure vocabulary as task evidence, accepting category-template prose instead of reading the abstract, and failing to identify the input, output, and executable success test. Typical false positives included federated or edge-LLM surveys, inference engines, MLOps and build-system surveys, cloud/IaC/AIOps benchmarks, deployment or routing agents, quantization and KV-cache methods, hardware acceleration, and generic sandbox or observability systems. In future audits, reject or reroute each such item based on its central artifact, and never use a sentence such as “adds environment-setup coverage” as the inclusion rationale.
- **Vendor CUA/model-card intake**: when refreshing `Computer Use (GUI)` or similar model sections, do not search only paper titles. Query each vendor, model family, lab name, and Chinese product name with `OSWorld`, `AndroidWorld`, `ScreenSpot`, `WebVoyager`, `Mind2Web`, `BrowseComp`, `WebWalkerQA`, `GUI grounding`, `computer use`, `phone use`, and `手机/屏幕/操作/智能体`. 4. Sort entries by release time when dates are known. Normalize all sort keys to the same `YYYY-MM` scale: an arXiv ID such as `2506.xxxxx` means `2025-06`, not integer `2506`; a conference-only entry uses the proceedings month or an explicitly recorded public-release month. For model-card-only, closed, or internal evaluations, place them by the model card or report date and explicitly mark that the task set is not publicly released.
5. Select the discovery anchor from the request. For a latest-conference or named-track request, sweep the official accepted-paper source before doing topic search. For a seed/topic request, search recent surveys first to map task boundaries, benchmark families, terminology variants, and common baselines.
6. For every user-provided seed that leads to a meaningful candidate, write a short discovery-channel reflection in `.tmp/<task>/`: where the seed could have been found, which aliases and channels exposed it or failed, which sibling searches should now be run, and which durable rule or source should be promoted. For open-source projects, confirm whether a paper actually cites the URL, slug, title, or verified official variant before calling the project paper-backed. ## Citation And Reference Closure

Use this loop when the user asks to close over all already included papers or to continue citation/reference expansion.

### Closure Integrity Gates

- **Bounded long-document reading**: Never load a long Markdown file, source inventory, candidate ledger, large JSON array, or aggregated subagent output wholesale into model context. Start with `wc`, headings, and targeted `rg`; then read fixed line ranges with `sed` or `nl`, stream records through a script, or split them into stable bounded chunks. Every subagent prompt must name its exact range or chunk files and repeat this constraint. Persist compact findings under `.tmp/` so later agents do not need to reread the full source. Apply the same rule to machine ledgers: inspect schema and counts first, split arrays with `split_json_chunks.py`, assign exact chunk paths, and aggregate through scripts.
- **Source inventory is independent of application coverage**: Processing every row in a local application, shortlist, applied-record, or candidate file proves only coverage of that derived file. Independently enumerate the canonical source inventory, normalize identifiers and aliases, left-anti-join it against current docs and every application ledger, and terminally review every missing source row. Report source total, represented total, missing total, verified aliases, inclusions, and rejections separately.
- **Two-level parent QA for bulk includes**: Treat every high-volume raw `include` set as untrusted input. First-level parent QA must cover exactly every raw proposed inclusion and decide `include`, `keep`, `reject`, or `reclassify` from abstract or full-text evidence, current taxonomy, adjacent routes, and domain exclusions. A second independent strict QA must cover exactly the first-level retained set and may reject or reclassify it again. The finalizer must fail closed on missing, extra, duplicated, unresolved, or nonterminal identifiers; no `deferred` row may survive, and neither a generator nor the first reviewer may certify its own retained set.
- **Closure JSON contract**: Distinguish JSON arrays from JSONL explicitly. `split_json_chunks.py`, `finalize_parent_qa_round.py`, and `apply_bilingual_tldr_rewrites.py` consume one valid JSON array per file; standalone object lines must be normalized first. Validate `type == "array"`, object rows, exact row count, canonical identifier uniqueness, and input-to-decision order. Every `reclassify` row needs a nonempty `target_doc` and `section`; every retained row needs a title, stable URL, paired target files, valid section, and concrete bilingual TLDRs. Never infer validity from `wc -l`.
- **Review-field compatibility**: Before passing a review JSON into an older apply or parent-QA script, inspect its accepted field names and normalize `tldr_en/tldr_zh`, `section`, `target_doc`, and `decision` into the script's contract. A successful insertion count is not proof that the evidence survived: verify the exact final Markdown bullets and scan for fallback phrases such as `Adds a ... item relevant to this capability area` and `补充该能力方向下的相关工作`. Use `apply_bilingual_tldr_rewrites.py` to restore concrete bilingual TLDRs by URL when a compatibility layer has fallen back to generic prose.
- **QA provenance invalidation**: Build keep lists and QA packets only from the current validated review set. If any review chunk is replaced, regenerate all dependent keep lists, QA packets, and QA decisions; before finalization, require exact identifier equality between current proposed includes and every QA stage, and fail on both missing and extra rows. ## Multi-Agent Intake Discipline

Use this when a task is broad enough to justify subagents.

1. Give each subagent a disjoint venue group, file group, or candidate chunk. Include explicit read/write ownership; by default, subagents write only `.tmp/` reports and do not edit official Markdown or this skill.
2. Require structured outputs: source list, candidate decisions, destination category, reason, uncertainty, duplicate or alias notes, `rg_en` and `rg_zh` status, evidence URL type, and URLs that still need parent verification.
3. If `rg_en` and `rg_zh` disagree, downgrade the candidate to `needs bilingual sync check` until the parent inspects both paired files. This prevents a duplicate entry from hiding an existing bilingual drift.
4. Require a separate lessons-learned memo from each subagent before closing the task. The memo should name concrete failure modes, not generic advice: missing official tracks, proceedings pages that hide titles, paper-title versus benchmark-name drift, Unicode or punctuation-sensitive names, unstable project URLs, over-broad category matches, or duplicate primary listings. It should also state input files, output files, whether Semantic Scholar or network APIs were called, whether official docs were edited, decision counts, and any incomplete phase. If interrupted, the subagent should still write a partial memo.
5. Keep parent review authoritative. The parent re-reads current docs, checks staged and unstaged diffs, normalizes aliases across English and Chinese files, verifies new URLs, and performs final edits as a single writer.
6. Convert repeated subagent lessons into durable skill rules or scripts. If several agents needed the same ad hoc command, promote it into `scripts/`; if several agents hit the same classification ambiguity, add a taxonomy rule or `Other` placement guidance here.
7. In the final user report, state whether subagent lessons were collected, where the memos live, what rules were added, and which phases remain bounded rather than complete.

## Candidate Screening

Accept candidates that clearly fit one of these roles:

- **Leaderboard**: official or widely used public ranking with enough task specificity to help readers locate current systems.
- **Survey**: recent or high-impact review, survey, tutorial, position, taxonomy, or systematic-literature paper that maps a capability area rather than introducing only a narrow benchmark or method.
- **Bench**: evaluates a capability with a defined task, dataset, protocol, leaderboard, or metric.
- **Model**: contributes a model, training recipe, post-training method, model architecture, reinforcement-learning algorithm, synthetic-data generation method, world model, alignment method, or other model-side technique that is clearly relevant to the capability page. Model-only work should go here, not be forced into Agent Harness or Bench.
- **Agent Harness**: contributes prompting, workflow orchestration, tool use, memory, multi-agent collaboration, environment management, verification, or other model-external execution logic.
- **Skill**: provides reusable agent capability packages, skill runtime infrastructure, skill benchmarks, skill creation, skill selection, skill safety, or skill portability.

Reject or defer candidates when:

- the work is too narrow or off-axis for the capability taxonomy even as Survey or Model;
- the contribution is primarily compression or inference acceleration without a capability-specific model, evaluation, or deployment relevance;
- the paper is only a narrow domain application that does not broaden the target capability taxonomy;
- it duplicates a stronger existing entry without adding a distinct axis;
- the project link is inaccessible and no stable paper or repository URL exists.

Classification reminders:

- Titles containing agent, tool, skill, benchmark, safety, or attack are not enough for inclusion; classify by the reusable asset and evaluated capability.
- Agent, multi-agent, framework, pipeline, and workflow wording must not override model-side evidence. If the contribution trains a model, optimizes a policy, learns a reward/verifier/controller/world model, distills trajectories, synthesizes training data, adapts weights, or changes decoding/logits/representations, route it to `Model` unless the paper's reusable artifact is clearly external runtime logic.
- Operations papers for building, deploying, monitoring, debugging, and maintaining agent systems usually belong with Software Development or Agent Harness infrastructure, not with a downstream application page such as Research unless the operational loop is specific to scientific work. `AgentOps` is the reference example.
- General theoretical work about agent world models, latent predictive environment models, or model-side prerequisites belongs in `Model` or a cross-cutting `Other` page unless the paper contributes a concrete external workflow harness.
- Do not reject model-only, training-only, architecture, reinforcement-learning, or synthetic-data papers solely because they lack an external agent harness. If they are relevant to the page's task axis, classify them under `Model`; if they only summarize a field, classify them under `Survey`.
- In robotics, reinforcement learning, and control papers, "skill" often means a learned policy skill, not this repository's packaged agent skills. Do not place such papers in Skill Use unless the work is about reusable agent skill artifacts, runtimes, selection, portability, or safety.
- Terminal-only surveys are rare; it is acceptable to include adjacent operating-system, coding-agent, or tool-use surveys only when the note clearly states the scope. Robotics survey candidates often use "skill" for motor policies rather than reusable agent skills, so classify them by the actual reusable artifact and not by the title word.
- Embodied/VLA entries should involve interactive physical, simulated, game, robotic, or action-feedback environments. Passive video understanding or generative world-model diagnostics usually belong in Video, Spatial, or Multimodal Generation unless the embodied action loop is central.
- For 3D and robotics-adjacent candidates, distinguish the artifact rather than the vocabulary: rigging, skinning, 4D reconstruction, Gaussian splatting, and static asset generation usually belong in Spatial or Multimodal Generation `Model`; robot policies, affordance learning, active view planning, embodied datasets, and XR interaction loops belong in Embodied/VLA; "skill" in robotics usually means a learned motor policy, not this repository's packaged agent skills.
- Video anomaly and generated-media candidates should be routed by contribution: datasets, authenticity protocols, and detector stress tests go to `Bench`; surveys and metric reviews go to `Survey`; VLM/LLM captioning, explanation, alignment, tokenization, and generation backbones go to `Model`; only explicit external orchestration loops go to `Agent Harness`.
- Cybersecurity entries should involve concrete cyber operations, environments, exploitation, defense, or security evaluation protocols. Generic jailbreak, red-team, or safety-judge work usually belongs in Agent Safety or Benchmark Reliability.
- **Research topic gate**: first require explicit evidence that an AI system automates, assists, or evaluates at least one substantive research action. Qualifying actions include scientific question answering; literature retrieval, reading, and synthesis; hypothesis or idea generation and selection; experiment design, execution, and analysis; result interpretation; reproduction or replication; scholarly writing, review, rebuttal, citation, integrity checking, and artifact promotion; and the general Data Science or ML-research lifecycle. The latter explicitly includes AI-driven data discovery, curation, cleaning, wrangling, exploratory analysis, statistical or causal analysis, feature engineering, analysis-code generation, model construction, training, evaluation, tuning, comparison, visualization, reporting, notebook execution, and benchmark-directed ML experimentation. These Data Science workflows do not need to mention a paper or a scientific hypothesis explicitly: automating them is itself automation of an important research stage. The AI must perform, assist, or be evaluated on the action. A non-AI estimator, prediction architecture, statistical theorem, deterministic data library, passive repository, or infrastructure component does not qualify merely because researchers could use it.
- **Research action test**: ask what concrete work the AI performs. Include an LLM or agent that turns data and an analytical objective into cleaned data, executable analyses, trained and compared models, interpretable findings, figures, or reports; include methods and benchmarks that improve or measure that capability. Exclude a paper whose output is only a new estimator, predictor, equation solver, database, workflow registry, or visualization library and in which no AI chooses, executes, checks, or explains the research workflow. Do not require `scientific`, `research`, `hypothesis`, or `paper` in the title or benchmark framing, and do not reject generic Data Science, AutoML, ML-engineering, Kaggle-style experimentation, or causal-analysis agents solely because their tasks are domain-neutral.
- **Algorithmic discovery boundary inside Research**: an agent UI is not required. Keep a trained method when its primary output is itself a research result or research decision, such as a discovered causal graph, symbolic law, governing equation, candidate hypothesis, experiment design, selected analysis pipeline, or empirically compared ML solution. These methods automate causal discovery, symbolic regression, system identification, scientific model discovery, or another substantive analysis stage. By contrast, exclude a conventional predictor, estimator, representation learner, numerical accelerator, or domain model that only maps fixed inputs to fixed labels or parameters and is not designed or evaluated as AI execution of a research action. The test is the automated epistemic action and output, not whether a scientist could use the model.
- **Research section test**: apply this only after the topic gate. `Survey` is for a survey, taxonomy, position, or systematic review whose primary object is AI automation of scientific work, including Data Science agents and automated ML-research workflows, not a generic survey of a non-AI scientific method. `Bench` includes a reusable dataset, task suite, metric protocol, evaluation population, leaderboard, standardized comparison, or a substantive empirical capability/reliability study that measures an AI system performing a named research step. A paper need not release a new benchmark: a controlled comparison, user study, failure analysis, or reliability audit is in scope when its object is whether or how AI performs research question answering, ideation, experiment design or execution, data analysis, reproduction, writing, review, rebuttal, citation, or another qualifying research action. Do not reject such a study merely because it evaluates one model, one workflow, or an existing task collection. Simulations that only validate a non-AI estimator remain out of scope. `Model` requires a trained or adapted model, architecture, objective, reinforcement-learning method, synthetic-data recipe, verifier, or decoding method whose purpose or evaluation is to improve AI scientific QA, literature work, ideation, data analysis, ML experimentation, reproduction, writing, review, or end-to-end research. `Agent Harness` is for model-external prompting, tools, workflow orchestration, memory, verification, or multi-agent execution that actually carries out one of those steps. `Skill` is for an executable agent-facing package, skill runtime, selection/portability mechanism, or skill benchmark for scientific work, including packaged Data Science and ML-experimentation skills. Route a literature-only retrieval, screening, evidence-synthesis, or source-grounded report artifact to `Deep Research`; keep Data Science, peer review, rebuttal, experiments, paper production, and other non-literature-only scientific workflows in `Research`.
- **Skill packaging precedence**: a repository remains in `Skill` when its primary released artifact is one or more installable `SKILL.md` packages, marketplace skills, host commands, plugins, or reusable prompt-and-script capability bundles, even if one package coordinates a long workflow. Use `Agent Harness` when the primary artifact is a standalone application, service, multi-agent system, runtime, or end-to-end framework and any skills are merely internal components. Do not reclassify an explicitly packaged scientific skill to Harness solely because it has multiple stages, agents, quality gates, or persistent state.
- **Research domain gate**: a domain dataset or example is not by itself disqualifying, but the artifact must expose a research step or model behavior that transfers beyond that domain. Reject vertical systems whose target, labels, workflow, evaluation, and claimed utility remain tied to medicine, biology, chemistry, geospatial sensing, ecology, finance, or another specialty without a general scientific-automation contribution. Preserve explicit user-requested exceptions only when the requested artifact is documented as such.
- Agent Safety MCP entries should distinguish security scanners, runtime proxies, protocol specifications, debuggers, and vulnerability databases. Prefer scanners and runtime proxies for `Agent Harness`; use official specs and databases as background unless they define a reusable evaluation or enforcement protocol.
- Agent Safety CUA entries need an explicit safety axis such as prompt injection, privacy leakage, unauthorized action, policy violation, harmful action, or runtime enforcement. Ordinary GUI completion, grounding, and robustness benchmarks usually belong in Computer Use GUI rather than Agent Safety.
- Memory and privacy candidates belong in Agent Safety when memory, tool arguments, inter-agent messages, logs, or planner state are treated as attack surfaces or control surfaces. Plain recall, personalization, or output-only privacy tests usually belong in Memory or general safety instead.
- In dense safety pages, short aliases are dangerous duplicate keys. Disambiguate lookalikes such as `AgentSafe`, `AGENTSAFE`, `Agent-SafetyBench`, `SafeAgentBench`, `Agent Security Bench`, `OpenAgentSafety`, `MCPInspect`, `MCP Inspector`, `DRIFT`, `Agent-in-the-Middle`, and `AiTM` with full titles, acronyms, and arXiv IDs before editing.
- Cross-cutting agent-system evaluation work that measures model-harness, agent-architecture, or framework effects across many task families belongs in `00-introduction/03-evaluation-methodology.md` unless one capability axis clearly dominates. `PawBench`, `General Agent Evaluation`, and `MASEval` are reference cases; do not force them into Agent Safety just because their task mix includes safety slices or OpenClaw-related examples.
- When a project name collides with unrelated public sites, verify the official owner/repository and live leaderboard before editing. For example, `agentscope-ai/PawBench` and `agentscope-ai.github.io/PawBench/` are the agent-evaluation project, while `pawbench.com/about` is an unrelated pet-testing site. Do not confuse that with `pinchbench.com/about`, which is the official PinchBench about page and is linked from `github.com/pinchbench/skill`.
- Aggregated model-harness benchmarks can expose standalone source benchmarks that deserve their own entries. PawBench is the reference case: after adding the aggregate, read source repositories such as `SKYLENAGE-AI/QwenClawBench` rather than leaving them as name-only provenance. Include a source benchmark when its README defines an independent task set, execution protocol, scoring rule, or leaderboard, such as QwenClawBench's 100 OpenClaw tasks, Docker isolation, anomaly marking, resumable runs, and penalized hybrid scoring.
- Do not assume a source suite is closed merely because an aggregate benchmark samples from it. If the upstream suite has its own current leaderboard, task repository, version, or broader task distribution, give it an independent inclusion decision. PinchBench is the reference case: PawBench v1.0 samples PinchBench tasks, but `pinchbench.com` and `pinchbench/skill` define a live OpenClaw benchmark over real tasks such as scheduling, email triage, research, coding, file management, memory, and skill discovery.
- If a chronology audit flags a title-only override collision, prefer a less ambiguous display name rather than weakening the audit. For example, avoid generic strings that match vendor model-card overrides when a paper-specific acronym is available.
- If an acronym already names another primary entry, keep the URL and title but change the display name to a descriptive variant before applying, such as `AEGIS Video Authenticity` rather than a bare `AEGIS`. The same rule applies to short aliases such as `CAT`, `CLEAR`, `D3`, `SDD`, `C2C`, `SMURF`, and `VADER`.

## Evidence And Writing

- Prefer English academic sources, especially conference papers, arXiv papers, official project pages, official repositories, and benchmark leaderboards.
- Use arXiv URLs when a paper exists. If no paper exists, do not force a paper link.
- Cite industry, product, and leaderboard facts adjacent to the claim.
- Treat Semantic Scholar candidates as candidates only; read the source before adding it.
- Keep a claim-evidence map for substantive edits. Each new paragraph or entry should have a reason to exist, a source that supports it, and a clear category.
- Never write placeholder survey prose. Each survey entry must summarize the work's most distinctive organizing lens, taxonomy, method family, evidence source, or risk boundary in one concrete sentence.
- Never write placeholder TLDR prose for any section. Each Bench, Model, Agent Harness, and Skill bullet should name a concrete dataset, protocol, model mechanism, training recipe, workflow loop, tool interface, memory/retrieval component, simulator, or packaged skill behavior. Avoid phrases such as "adds coverage", "capability-taxonomy", "focusing on the capability signal stated in the title", "workflow, tool loop, retrieval pipeline", and their Chinese equivalents unless the sentence also names the concrete contribution.
- When rewriting an Agent Harness entry, read at least the abstract or official project summary and identify what is external to the base model: orchestration, tools, memory, retrieval, environment control, verification, multi-agent collaboration, or human-in-the-loop control. If the abstract only describes training, model architecture, reinforcement learning, synthetic data, forecasting, reconstruction, or world modeling, move it to `Model`; if it describes a dataset, simulator-as-evaluation, fuzzer, safety test, or metric, move it to `Bench`.
- Placeholder cleanup is also a taxonomy audit: after rewriting prose, run a residual placeholder scan across both the source section and every moved-to destination, inspect the diff for newly added or moved entries, and ask whether each destination still matches the paper's actual contribution. Treat `title_repeated_after_colon` findings as formatting cleanup unless the remaining summary is also semantically generic. Treat bilingual URL-set checks as structural checks only; semantic alignment still requires changed-row review, especially when subagents or scripts were interrupted mid-batch.
- Separate official baselines, reproduced baselines, local modified runs, retry runs, and leaderboard systems; do not merge incompatible evaluation protocols.
- Put citations near the claim they support, not in a bundle at the end of a long sentence.
- For this standalone repository, keep English `*.md` and Chinese `*.zh.md` semantically aligned outside any future `research/` directory.
- Avoid symbolic shorthand such as `/` and `+` in narrative prose; use explicit conjunction phrases.

## Notes

- Keyword search misses many relevant works. Combine keyword search, survey reading, baseline inspection, references, citations, GitHub search, and leaderboard inspection.
- For open-source project intake, URL-citation search is mandatory before classifying a project as paper-backed. Search exact URLs, protocol-less URLs, slugs, README titles, repository descriptions, package names, marketplace names, and `SKILL.md` names. Confirm citations from actual paper or reference evidence, not snippets.
- When no citing paper is found for an open-source project, keep the project as project-only or defer it; record searched keys and channels in `.tmp/` and avoid claiming that no paper exists.
- GitHub redirects, renamed repositories, forks, mirrors, and deep `blob` or `tree` URLs must be normalized before deduplication. Search both old and new slugs because papers may cite either.
- If the user excludes a domain such as biomedical work, carry that exclusion through keyword search, citation traversal, URL-citation search, subagent instructions, and final screening. Record excluded hits only as skipped or rejected ledger rows.
- Each intake should include a discovery-channel reflection: for every meaningful seed, state where it should have been discoverable, which aliases and channels were used, what failed, and what sibling searches the seed suggests.
- When a user asks to include exploratory candidates, do not leave useful `defer` rows only in `.tmp`. If a candidate is relevant but not a benchmark or runnable harness, place it in the closest honest section as a roadmap, resource, project-only skill, or neighboring-category entry with an explicit caveat.
- A newer arXiv result for the same repository is not automatically a replacement for the older entry. Verify title, authors, task set, and date first; if both are real, keep the original historical entry and add the newer follow-up only when it contributes a distinct evaluation angle.
- For skill suites, marketplace results are incomplete. Always combine `skills find`, `clawhub`, SkillNet, GitHub repository search, exact repo slug search, README title search, and direct `SKILL.md` inspection before deciding that a popular skill project is absent.
- Fresh proceedings and benchmark tracks are especially easy to miss through keywords or citation graphs: titles may use project names rather than task terms, accepted papers may have sparse citation edges, and some works may temporarily have only an official venue page. Use official venue enumeration as the recall anchor.
- Semantic Scholar closure broadens a seed set but does not certify coverage of a newly accepted conference track. Preserve and report official-track coverage separately from citation-graph expansion.
- Semantic Scholar citation results are noisy. Rank by fit first, then recency and citation count; do not add every candidate just because it appears in the graph.
- Repeated Semantic Scholar `429` should trigger bounded exponential backoff, not a search-strategy downgrade. Keep `--max-delay 5`, set `--delay-decrease 0` during cooldown, keep one parent-owned process running until the retry budget is exhausted, and use the partial cache plus final `s2_edges.md` to screen candidates or report bounded closure.
- Survey papers are useful twice: they identify taxonomy and expose baselines that should be checked as potential landscape entries.
- Adding a new section type changes the meaning of old rejections. Revisit previous `model-only`, `training-only`, `architecture-only`, and `survey-only` rejects before declaring coverage complete.
- In task pages, keep section order stable as `Leaderboard`, `Survey`, `Bench`, `Model`, `Agent Harness`, `Skill`. Empty sections are acceptable when no credible entries are found; missing sections are not acceptable during structure-normalization tasks.
- In the split tree, section order is represented by filenames as well as headings. Adding `04-model.md` requires renumbering downstream section files to `05-agent-harness.md` and `06-skill.md` in both languages, plus updating local `README.md` links.
- The old flat numbered docs are useful compatibility inputs but should not be used as output paths. Scripts that receive flat paths must resolve them to split section files through `resolve_english_target_doc`.
- When moving method papers from `Agent Harness` to `Model`, remove duplicate primary listings unless the same work also contributes a distinct external harness. Model entries should summarize the model-side contribution; Agent Harness entries should summarize execution logic.
- Research-page classification must start from the durable artifact, not the presence of "agent", "framework", "workflow", or "evaluation" in the title. Originality, novelty, reviewer-matching, paper-quality, reproducibility, or idea-judgment works with defined datasets, scoring protocols, comparison tasks, or reliability studies belong in `Research / Bench` even if they evaluate agents; `What Is Novel? / Are We Truly Innovating?` and `LitBench` are reference cases. Works that train, post-train, learn a reward or verifier, synthesize training tasks, build a learned judge, optimize agent policies, or use learned/test-time evolution with reward-model signals belong in `Research / Model` unless the external orchestration is the clear primary contribution; `DeepInnovator`, `FlowPIE`, `AI Scientist via Synthetic Task Scaling`, `MAGNET`, `DataPRM`, and `AutoLLMResearch` are reference cases.
- Closure status has two layers. It is valid to report the checked-paper registry as locally closed when `checking == 0`, `deferred == 0`, and S2 has no fetchable missing edges, but global closure is not complete while citation/reference traversal has produced unchecked candidates or chunk decisions are missing. State both counts explicitly, for example "existing registry closed; candidate closure open with N unchecked candidates and M chunks awaiting decisions."
- For Model chronology, arXiv IDs usually provide enough ordering, but official proceedings-only items need manual release keys such as conference month. Record or remember those keys during intake so a later audit does not silently pass with unknown dates.
- Benchmark names drift across papers, project pages, and leaderboards. Normalize names and verify whether variants are distinct tasks or aliases.
- Unicode, punctuation, hyphenation, and squared or Greek symbols can break exact matching. Normalize these variants for search, but preserve the canonical display name from the paper or project when editing docs.
- Canonicalize identifiers before deduplication: strip Markdown link syntax, trailing parentheses, ASCII punctuation, and Chinese punctuation from DOI or arXiv values, then compare normalized DOI, arXiv ID, URL, title, and aliases.
- Short acronyms are unsafe deduplication keys. Treat matches such as common words, two- to four-letter acronyms, or reused family names as hints until the surrounding title, URL, authors, arXiv/OpenReview ID, or repository confirms identity.
- Popular agent and skill projects often do not surface through generic benchmark keywords. For skill/open-source surveys, run a named-system pass over well-known project names, long-form expansions, repository slugs, and marketplace package names; ARIS is the reference failure mode because `ARIS` alone is noisy, while `Auto-Research-in-sleep`, `Auto-claude-code-research-in-sleep`, `research-pipeline`, `paper-writing`, and `skills-codex` expose the actual paper, repo, and skill entries.
- Screenshot or social-media skill lists need a source-family intake, not only exact-name search. For each visible name, search marketplace names (`skills find`, `clawhub`, SkillNet), GitHub exact slugs, README titles, `SKILL.md` filenames, plugin manifests, and common aliases; then classify by artifact shape. Add packaged `SKILL.md` repositories, Claude/Codex/OpenClaw plugins, and skill-backed CLI/tooling when the reusable behavior is clear. For Research skills, also run broad GitHub topic passes such as `academic skills`, `research skills`, `paper skill`, `Claude Code academic`, `scientific writing skill`, `empirical research skills`, `PhD skills`, `citation verification`, `paper to patent skill`, and `math modeling skill`; compound boolean-like GitHub CLI queries often return empty results, so use short keyword phrases and inspect README/SKILL.md manually. Defer app-only editors or dashboards unless the target section explicitly accepts skill-adjacent tools; Research does accept research-production editors when they materially structure scientific work. Reject keyword false positives from generic names such as `Happy-*`, `Sanity-*`, `Reference Manager`, or `Survey Builder` unless an official skill repository is verified. If a broad science bundle contains biomedical/clinical/database subskills, include only the general research, literature, citation, or methodology components and record the biomedical exclusion.
- Autoresearch-style projects are often project-only but still landscape-relevant when they define a reusable loop. Classify the original minimal loop as Agent Harness, generalized command packages as Skill, paper follow-ups that optimize the loop as Agent Harness, and curated lists such as awesome repositories as discovery resources unless they contain their own runnable harness.
- For metric-driven autonomous loops, capture the evaluation metric, fixed budget, editable file set, rollback rule, run log, and safety assumptions. These details matter more than star count when deciding whether the artifact is reusable.
- Active leaderboards can contain systems without papers. Add them only when the system is relevant and the leaderboard or project URL is stable.
- Keep task boundaries clean when benchmarks use the same substrate. For example, cybersecurity benchmarks belong in the cybersecurity category even when they run in a terminal, and embodied or vision-language-action benchmarks belong in an embodied/VLA category rather than GUI-only computer use.
- When moving a benchmark to a new category, remove duplicate primary listings from old categories. Keep cross-references only when they explain a neighboring capability rather than re-listing the benchmark as part of that category.
- Cache per paper and per edge list so interrupted Semantic Scholar runs are recoverable.
- Treat empty citation-cache files as valid only if they contain a successful response with empty `data`; re-fetch malformed or truncated JSON.
- Do not let several subagents hit Semantic Scholar in parallel. Use one serial scanner, or a shared file lock and cache, while subagents do reading and screening from saved reports.
- Keep candidate provenance such as `candidate cites arXiv:<seed>` or `seed references arXiv:<candidate>` in `.tmp` reports so rejected and accepted items remain auditable.
- Use GET fallback when HEAD fails. Some sites block HEAD even when the page is accessible.
- Reuse the project-local URL cache for routine checks. A URL checked in the last month should not be fetched again unless a focused verification requires `--refresh-cache`.
- Report URL checks in three classes: successful, soft-blocked or rate-limited, and broken. A blocked dynamic page needs manual replacement only when a better stable URL exists.
- A broad URL check can surface pre-existing 404s unrelated to the current edit. Do not hide them, but do not conflate them with newly added links; run a narrow check for new pages or new URLs before final reporting.
- A chronology bug can arise when script keys mix compact arXiv months (`2506`) with four-digit conference years (`2025`). Never compare those raw forms directly; normalize to `YYYY-MM` first, then audit the resulting section order after insertion.
- Chronology audits can pass vacuously if entries were moved to a new category file but the destination file is omitted from the audit set. Prefer running the recursive default audit, and include both English and Chinese section files when narrowing the check.
- If a diff shows many deletions after a category migration, first check whether the entries were deliberately moved into a new category before treating the diff as data loss. Migration review should compare source and destination URL sets, not just line counts.
- For GitHub code links, prefer checking the repository itself rather than only the HTML page status.
- Give each subagent a disjoint file scope or a read-only report path under `.tmp/`.
- Prefer single-writer final edits: subagents write memos, while the parent agent merges into official Markdown files after rereading current file contents and `git status`.
- In dirty worktrees, inspect both `git diff` and `git diff --cached` for relevant files. Some agent sessions leave files staged as additions, so `git diff --stat` alone may under-report the actual content being edited.
- Before diagnosing a problem from `git diff`, distinguish staged migration work, unstaged script fixes, and user edits. Use both `git diff --stat` and `git diff --cached --stat`; do not infer accidental deletion solely from one side.
- In closure rounds, require every subagent chunk to include machine-readable decisions, a short rationale, duplicate or alias notes, destination doc/section, and a separate lessons memo. Parent sync should reject placeholder or undersized outputs rather than assuming a file exists means the chunk was reviewed.
- In closure rounds, treat rejection recall as an independent review stage: merge only exact terminal `include` or `reject` decisions, then send every recovered include through parent QA again. Do not let a plausible rejection rationale, a keyword-only vertical signal, or a missing abstract silently terminate a candidate; record the bounded channels searched and the terminal reason.
- In closure rounds, compare normalized DOI, arXiv ID, title, authors, and abstract before applying candidates. A proceedings DOI and an arXiv full version for the same work get one primary EN/ZH bullet and one terminal included alias; aliases must not seed a second documentation entry or closure round. QA overrides are applied before inclusion counts, document generation, registry updates, and seed extraction.
- Finalizer reason precedence is deterministic: `strict reason_en > parent reason_en > review reason_en > legacy reason > note`. Empty later fields must not erase a nonempty earlier reason. When a QA action is `alias`, require a valid canonical target, inherit its section and paired document paths, emit no apply row for the alias, and terminally record `alias_of`.
- Before applying accepted candidates, run parent QA for exact duplicates, conceptual overlap with existing entries, adjacent-category misplacement, and short-acronym collisions. The most common false positive is not an exact duplicate; it is a narrow domain paper or model-side method that resembles a reusable benchmark or harness only by title.
- Store closure round artifacts under stable `.tmp/candidate_closure_roundN/` paths: `chunks/`, `decisions/`, `memos/`, `target_overrides.json`, `applied_inclusions.json`, `included_for_registry.json`, and reports. This makes context compression and handoff survivable.
- Treat generated candidates from references and citations as noisy discovery signals. A candidate is not accepted until a reader verifies the paper's actual contribution, baseline or evaluation protocol, relation to this repository's taxonomy, and a stable official URL.
- Agent Harness entries should emphasize workflow, tool orchestration, memory, environment interaction, verification, or multi-agent design.
- Skill entries should point to real skill artifacts, skill runtimes, skill benchmarks, skill safety work, or skill portability infrastructure.

## Hard Rules

- Do not rely on keyword search alone for paper discovery; use citation and reference traversal.
- Do not classify an open-source project as paper-backed until a URL, slug, title, `SKILL.md` name, or verified official variant is found in the paper, PDF, HTML bibliography, reference metadata, appendix, official project page, or repository reference.
- Do not treat "no search result" as "no citing paper exists"; report bounded negative evidence with searched keys and channels.
- Do not ignore user-specified domain exclusions during citation expansion or URL-citation search.
- Do not close an intake without reviewing the discovery-channel reflection for user-provided seeds that produced meaningful additions.
- When the request concerns latest papers from a named conference or track, do not rely on arXiv, keyword search, or citation traversal as the primary inventory; enumerate the official accepted-paper source first and record that sweep.
- Do not claim citation or reference closure is complete when an API was rate-limited, unavailable, or only partially scanned; report the bounded evidence actually collected.
- Do not add leaderboard, product, or adoption claims without an adjacent citation or URL.
- Do not append new Bench, Model, Agent Harness, Skill, or Leaderboard entries out of chronological order when release dates are available.
- Do not finish a multi-file inclusion run without checking edited Bench, Model, and Agent Harness sections for chronological inversions in both English and Chinese.
- Do not treat training-only model papers as core Agent Harness entries unless the harness/workflow design is the contribution.
- Do not classify a paper or project as Environment Setup from infrastructure, deployment, runtime, cloud, DevOps, MLOps, AIOps, sandbox, or observability keywords alone; require abstract-level evidence for a concrete target environment, setup/build operation, executable verification, and recovery loop, and apply the section-specific artifact rules above.
- Do not leave broken newly added URLs in the repository.
- Do not let parallel subagents edit overlapping files without explicit file ownership.
- Do not close a multi-agent intake without collecting or explicitly waiving subagent lessons-learned memos.
- Do not deduplicate or exclude a candidate based only on a short acronym match.
- Do not mark a candidate `included` in the checked-paper registry until the English and Chinese Markdown entries have actually been added or the candidate is already present in both languages.
- Do not run several Semantic Scholar scanners at once, even if each scanner has local delay logic.

- **Research closure and repository-link decisions**: for Research pages, decide repository links by artifact value, not by availability alone. Add official code/data/leaderboards when they reproduce a listed benchmark, model, or harness; do not add project-only repositories to Research merely because they exist. Route literature review, survey generation, literature screening, citation-system audits, source-grounded report writing, and RAG-only scholarly search to Deep Research. Reject or move biomedical, geospatial, climate, chemistry, or other narrow vertical systems unless the paper exposes a reusable research workflow, evaluation protocol, or model-side method that transfers beyond the domain. During parent closure, do not leave `candidate`, `centered on title`, `externalize workflow`, or `提供可复用 agent 工作流` rows in official docs; either rewrite from abstract/full text, move to the right category, or remove from the primary Research list.
- **Canonical DOI cache keys**: DOI matching is case-insensitive. Normalize DOI payloads to lowercase before deriving Semantic Scholar cache paths or comparing documentation identifiers; otherwise publisher-style uppercase components such as `IEEE-CH` create false missing-edge reports and duplicate fetches.
- **DOI URL rewrite matching**: DOI URLs can differ only in case between metadata, generated bullets, and existing Markdown. Rewrite and verify DOI-linked bullets case-insensitively while preserving the document's canonical spelling; exact string matching otherwise creates false missing rows and leaves stale TLDRs behind.
- **Triage exclusions are provisional evidence**: an automatic low-signal or biomedical reject must still enter the round's terminal ledger with its exact triage reason. Do not let auto-rejected rows disappear when review chunks are merged; validate that `reviewed + auto-rejected == unchecked candidates` before registry marking.
