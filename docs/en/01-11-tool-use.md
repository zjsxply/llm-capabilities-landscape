# 1.11 Tool Use

> Parent chapter: 1. Foundational Capabilities


## 1.11.1 Leaderboard

- [BFCL / Berkeley Function-Calling Leaderboard](https://gorilla.cs.berkeley.edu/leaderboard.html): A continuous leaderboard suitable as the main reference for pure function calling.
  It focuses on isolating tool selection, argument filling, schema following, and multi-turn call accuracy, making it more suitable for comparing structured invocation capability in models/agents than full software-engineering execution capability.
- [τ-bench / τ²-Bench](https://www.taubench.com/) ([τ²-Bench submission instructions](https://github.com/sierra-research/tau2-bench/blob/main/docs/leaderboard-submission.md)): A leaderboard/submission workflow for multi-turn tool use with stateful APIs.
  Its value lies in connecting customer service, business rules, database state, and tool returns into executable tasks, making it suitable for screening agent scaffolds that handle realistic API orchestration.
- [Tool Decathlon (Toolathlon)](https://toolathlon.xyz/): A public leaderboard for cross-application, multi-tool, long-chain tasks.
  Compared with BFCL's function-signature prediction, it is closer to MCP/real-application toolchain settings, making it suitable for observing whether agents can complete tasks reliably under many tools, cross-application state, and dedicated checking scripts.
- [Claw-Eval-Live](https://claw-eval-live.github.io/): A continuously updated workflow-agent leaderboard covering terminal, file, web, service, and skill-related tasks.
  It is not a pure function-calling leaderboard, but it is suitable as a cross-reference for tool-use, terminal-use, and skill-use, especially for observing transferability of agent harnesses on dynamic real workflows.

## 1.11.2 Bench

- [API-Bank](https://arxiv.org/abs/2304.08244) ([code](https://github.com/AlibabaResearch/DAMO-ConvAI/tree/main/api-bank)): What it evaluates: tool selection, argument filling, and multi-step calls by tool-augmented LLMs; core idea: protocolize tool sets and tasks, emphasizing executable call trajectories rather than pure-text answers.
- [Gorilla](https://arxiv.org/abs/2305.15334) ([code](https://github.com/ShishirPatil/gorilla)): What it evaluates: function/tool-calling capability under large-scale API connections; core idea: emphasize alignment with massive APIs and executable calls under function-signature constraints.
- [ToolQA](https://arxiv.org/abs/2306.13304) ([code](https://github.com/night-chen/ToolQA)): What it evaluates: correctness of answering questions through external tools, including multi-turn calls and use of tool returns; core idea: include the information gain from tool use in the evaluation protocol rather than only comparing fluency of language output.
- [ToolBench](https://github.com/OpenBMB/ToolBench) (source work: [ToolLLM](https://arxiv.org/abs/2307.16789)): What it evaluates: tool calling and multi-step execution over a large-scale set of real APIs; core idea: use API scale and executable evaluation as sources of pressure, covering tool retrieval, argument alignment, and execution-feedback loops.
- [BFCL / Berkeley Function-Calling Leaderboard](https://arxiv.org/abs/2409.00608): What it evaluates: accuracy and robustness of function calling, including tool selection, argument alignment, and schema constraints. Core idea: use standardized function signatures and a unified leaderboard to isolate language ability from invocation correctness. ([official leaderboard](https://gorilla.cs.berkeley.edu/leaderboard))
- [MTU-Bench](https://openreview.net/forum?id=6guG2OlXsr): What it evaluates: multi-granularity tool use by large language models. Core idea: vary tool-use difficulty across subtasks so evaluation is not limited to single-call function selection or final-answer correctness.
- [ToolSandbox](https://aclanthology.org/2025.findings-naacl.65/): What it evaluates: stateful conversational tool use. Core idea: combine a user simulator, implicit tool-state dependencies, intermediate milestones, and on-policy interaction so tools are evaluated in a changing environment rather than as stateless API calls.
- [MCP-RADAR](https://arxiv.org/abs/2505.16700): What it evaluates: tool-use capability under the MCP framework across six task categories: mathematics, search, email, calendar, files, and terminal; core idea: jointly measure answer correctness, operation accuracy, call turns, and resource efficiency, moving MCP from protocol support to quantifiable execution evaluation.
- [τ-bench / τ²-Bench](https://arxiv.org/abs/2506.07982): What it evaluates: multi-turn tool use and API orchestration, including choosing tools, filling arguments, reading returns, correction, and retry. Core idea: make executable correctness of the toolchain quantifiable instead of only checking language output.
- [DICE-BENCH](https://arxiv.org/abs/2506.22853): What it evaluates: tool-use capability in multi-turn, multi-party conversations, especially call correctness when function names and argument clues are scattered across turns and participants; core idea: measure dispersion of tool-related information with DICE-SCORE, then synthesize more realistic function-calling scenarios through tool dependency graphs.
- [ToolHop](https://aclanthology.org/2025.acl-long.150/): What it evaluates: multi-hop tool use over locally executable tools. Core idea: use query-driven tasks with tool interdependencies, execution feedback, and verifiable answers to test planning across tool chains.
- [CONFETTI](https://aclanthology.org/2025.acl-long.394/): What it evaluates: conversational function calling through turn-level interactions. Core idea: use human-simulated conversations with follow-ups, corrections, ambiguous goals, and implicit constraints to test whether models preserve function-call intent across dialogue turns.
- [LiveMCPBench](https://arxiv.org/abs/2508.01780) ([project page](https://icip-cas.github.io/LiveMCPBench); [code](https://github.com/icip-cas/LiveMCPBench)): What it evaluates: retrieval, routing, and composition in a large-scale, multi-server MCP tool space. Core idea: provide 70 servers and 527 tools, explicitly making "finding the tool" and "combining the tool correctly" the main bottlenecks for MCP agents.
- [MCP-Universe](https://arxiv.org/abs/2508.14704) ([project page](https://mcp-universe.github.io); [code](https://github.com/SalesforceAIResearch/MCP-Universe)): What it evaluates: long-horizon, multi-domain tool use on real MCP servers; core idea: combine real servers for navigation, repository management, financial analysis, 3D design, browser automation, and web search, and evaluate execution under unfamiliar tools and long-context pressure.
- [LiveMCP-101](https://arxiv.org/abs/2508.15760): What it evaluates: stress testing and diagnosis of MCP-enabled agents on real multi-step queries. Core idea: use 101 challenging queries, execution plans, and dynamic tool returns to check MCP agents' tool selection, scheduling, result handling, and failure recovery.
- [MCPVerse](https://arxiv.org/abs/2508.16260): What it evaluates: agentic tool use in the real MCP server ecosystem; core idea: replace static function signatures with executable MCP tool sets, examining tool discovery, argument binding, state tracking, and multi-step recovery.
- [MCP-Bench](https://arxiv.org/abs/2508.20453) ([code](https://github.com/Accenture/mcp-bench)): What it evaluates: MCP tool-calling agents on complex real tasks; core idea: make server/client connection, call trajectory recording, and task scoring into a reproducible benchmark-side harness.
- [MCP-AgentBench](https://arxiv.org/abs/2509.09734): What it evaluates: task performance of real language agents under MCP-mediated tools; core idea: use MCP as a tool middleware layer and test unified handling of tool descriptions, return values, environment state, and multi-turn plans.
- [MCPMark](https://arxiv.org/abs/2509.24002) ([code](https://github.com/eval-sys/mcpmark)): What it evaluates: stress testing for realistic and comprehensive MCP use; core idea: cover multi-server setups, multi-tool dependencies, stateful tasks, and exception recovery, making it closer to MCP production workflows than single-function calls.
- [VitaBench](https://arxiv.org/abs/2509.26490): What it evaluates: multi-step invocation capability closer to "real application toolchains," including multi-tool composition and result verification. Core idea: raise tool calling from "single function prediction" to "executable multi-step workflow."
- [TRAJECT-Bench](https://arxiv.org/abs/2510.04550): What it evaluates: quality of complete agentic tool-use call trajectories rather than just final answers; core idea: use executable tools and fine-grained metrics to check tool selection, parameterization, call order, parallel width, and chain depth, locating failures where the answer is right but the call chain is wrong.
- [Tool Decathlon (Toolathlon)](https://arxiv.org/abs/2510.25726): What it evaluates: long-horizon real task execution across 32 applications and 604 tools. Core idea: many tools come from MCP servers, and each task has a dedicated execution checking script, emphasizing cross-application state, toolchain length, and real initial environments.
- [NESTFUL](https://aclanthology.org/2025.emnlp-main.1702/): What it evaluates: nested sequences of API calls. Core idea: stress the planning pattern where one tool call's result must parameterize deeper calls, exposing failures hidden by flat function-calling benchmarks.
- [MCP-Atlas](https://arxiv.org/abs/2602.00933) ([code](https://github.com/scaleapi/mcp-atlas)): What it evaluates: multi-step tool orchestration on real MCP servers; core idea: use 36 real MCP servers, a containerized harness, and a claims-based rubric to test tool discovery, argument alignment, and recovery.
- [τ³-Bench](https://sierra.ai/uk/resources/research/tau-3-bench): What it evaluates: agentic customer-interaction tasks that extend tau-style stateful tool use toward knowledge retrieval and voice settings. Core idea: keep realistic policies, state, and tool constraints while adding knowledge and voice-agent pressure beyond the original text/API tau-bench setup.
- [MCP misleading tool-description measurement](https://arxiv.org/abs/2602.03580): Evaluates how agents behave when MCP tool descriptions disagree with implementation. Core idea: combine large-scale MCP server consistency analysis with agent-behavior tests so tool-use evaluation covers semantic description-code mismatch, not only argument filling.
- [Agent-Diff](https://arxiv.org/abs/2602.11224) ([code](https://github.com/agent-diff-bench/agent-diff)): What it evaluates: enterprise API tasks executed through code against sandboxed service replicas. Core idea: judge success by expected state differences rather than trace similarity, preserving realistic API interaction while making final outcomes deterministic and reproducible.
- [CCTU](https://arxiv.org/abs/2603.15309): What it evaluates: LLM tool use under complex constraints; core idea: explicitly write resource, behavior, tool-set, and response constraints into tasks, examining whether models can stably trade off tool choice, constraint following, and self-correction.
- [WildToolBench](https://arxiv.org/abs/2604.06185): What it evaluates: multi-turn, multi-step tool use under real user behavior; core idea: include compositional tasks, implicit intent across turns, and instruction switching to avoid overestimating tool-use ability on artificially regular tasks.
- [The Amazing Agent Race (AAR)](https://arxiv.org/abs/2604.10261) ([project page](https://minnesotanlp.github.io/the-amazing-agent-race); [code](https://github.com/minnesotanlp/the-amazing-agent-race)): What it evaluates: DAG-structured multi-step tools, web navigation, and arithmetic reasoning; core idea: separately diagnose navigation, tool calls, and result aggregation, targeting path-selection failures invisible to linear benchmarks.
- [UniToolCall](https://arxiv.org/abs/2604.11557): What it evaluates: unified representation, data construction, and evaluation for tool-use trajectories. Core idea: standardize public datasets and benchmarks into a Query-Action-Observation-Answer format, exposing single-turn, multi-turn, serial, and parallel tool-use patterns under compatible metrics.
- [Claw-Eval-Live](https://arxiv.org/abs/2604.28139) ([project page](https://claw-eval-live.github.io/); [code](https://github.com/Claw-Eval-Live/Claw-Eval-Live)): What it evaluates: continuously updated real workflow-agent tasks covering terminal, files, web, services, and skill-related toolchains. Core idea: generate task snapshots with fixtures, services, and graders from public workflow-demand signals and ClawHub skill signals, evaluating tool-use transferability through executable trajectories and artifacts.
- [AgentEscapeBench](https://arxiv.org/abs/2605.07926): What it evaluates: out-of-domain tool-grounded reasoning under long-range dependencies. Core idea: use escape-room-style tasks with tool and item dependency graphs, hidden state, and deterministic final answers to test whether agents can infer novel procedures rather than repeat familiar API workflows.
- [When2Tool](https://arxiv.org/abs/2605.09252) ([code](https://github.com/Trustworthy-ML-Lab/when2tool)): What it evaluates: when an agent should call tools and when it should answer directly; core idea: make tool necessity an explicit evaluation boundary, avoiding the mistaken interpretation that more tool calls mean stronger tool-use capability.
Note: This line is more about whether agents can correctly select tools, fill arguments, and handle multi-turn API orchestration, not just function-call accuracy.
- [ComplexMCP](https://arxiv.org/abs/2605.10787): What it evaluates: LLM agents in dynamic, interdependent, large-scale tool sandboxes; core idea: include tool state, cross-tool dependencies, and environment changes in scoring, specifically testing fragile points in long-chain MCP tool execution.
## 1.11.3 Agent Harness

- [ReAct](https://arxiv.org/abs/2210.03629) ([code](https://github.com/ysymyth/ReAct)) is the most common general agent-loop baseline for tool use: `reasoning -> action -> observation`. On multi-step toolchain tasks such as τ2-Bench and VitaBench, the main differences come more from runtime design, such as argument validation, retry, fallback, and state management, than from a specialized solver.
- [ToolLLM](https://arxiv.org/abs/2307.16789) ([code](https://github.com/OpenBMB/ToolBench)): A representative tool-use solver agent implementation that performs tool retrieval, argument alignment, and multi-step calls over a large-scale set of real APIs.
- [Factored Agents](https://arxiv.org/abs/2503.22931): A tool-use agent architecture that separates high-level planning and in-context learning from tool-format memorization. Core idea: use specialized components to reduce malformed, missing, and hallucinated API fields while preserving adaptability in dynamic environments.
- [Gradientsys](https://arxiv.org/abs/2507.06520): A multi-agent LLM scheduler with ReAct-style orchestration. Core idea: coordinate specialized agents through scheduling and feedback so multi-step tool or workflow execution is managed explicitly rather than left to a single monolithic prompt.
- mcp-use ([code](https://github.com/mcp-use/mcp-use); [docs](https://mcp-use.com/docs)): No standalone paper, but it provides MCP server, MCP app, Inspector, and deployment workflows, making it suitable as an engineering-side MCP tool-use harness, especially by combining tool definition, debugging, observability, and publishing in one SDK.
- [MCP-Universe](https://arxiv.org/abs/2508.14704) ([code](https://github.com/SalesforceAIResearch/MCP-Universe)): More of an agent harness at the tool-ecosystem layer than just a benchmark dataset; it organizes MCP servers, tasks, executor, UI, and evaluation records into one runtime environment, making it suitable for reproducible experiments and comparisons among tool-use scaffolds.
- [Meta-Agent-Workflow](https://doi.org/10.1145/3701716.3715247): A tool-use harness that constructs, retrieves, and refines reusable workflows for LLM agents. Core idea: turn repeated tool-use trajectories into workflow assets so later tasks can reuse and adapt structured execution plans instead of starting from a one-off ReAct loop.
- [ToolGate](https://arxiv.org/abs/2601.04688): A contract-grounded verified execution harness for LLM tool use. Core idea: represent trusted world state symbolically and gate tool commits through Hoare-style contracts so tool calls have checkable safety and state-evolution guarantees.
- [SkillGraph](https://arxiv.org/abs/2604.19793): A graph-prior framework for tool sequence recommendation. Core idea: mine execution-transition regularities from successful tool-use trajectories, then separate candidate retrieval from ordering so agents can plan data-dependent API chains instead of relying only on semantic similarity.
- [Planning Horizon in Data-Centric Tool Calling](https://arxiv.org/abs/2605.08477): Studies whether tool-using agents need explicit step-by-step planning in data-centric tasks. Core idea: compare planning horizons inside tool-calling workflows so agent scaffolds can choose when detailed decomposition helps or hurts execution.
- [RubricRefine](https://arxiv.org/abs/2605.09730): A reliability repair layer before tool invocation; the core idea is to first generate task/registry-specific rubrics and then correct inter-tool contract errors before execution.
- [AOP](https://www.semanticscholar.org/paper/2dccab11b1feb5424437a79f047c8a91c1818634): An automated and interactive LLM pipeline-orchestration harness for complex query answering. Core idea: let the system compose, inspect, and revise multi-step LLM pipelines instead of treating complex queries as a single prompt or fixed workflow.
## 1.11.4 Skill

- [langchain4j-tool-function-calling-patterns](https://skills.sh/giuseppe-trisciuoglio/developer-kit/langchain4j-tool-function-calling-patterns) is suitable for integrating function calling into engineering frameworks.
- [skill-validator](https://skills.sh/daffy0208/ai-dev-standards/skill-validator) can serve as an additional validation layer in tool-call chains.
