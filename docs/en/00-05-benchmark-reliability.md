# 0.5 Benchmark Reliability and Dynamic Evaluation

> Parent chapter: 0. Harness and Skill Creator

## 0.5.1 Why This Is a Separate Topic

As models and agents iterate faster, the main risks of static benchmarks are no longer just that questions are too easy. They also include question leakage, training contamination, leaderboard overfitting, judge drift, opaque evaluation protocols, unreproducible dynamic environments, and the illusion of "high score but not deployable." Reliable evaluation needs to examine four things at once: whether tasks are still fresh, whether metrics are interpretable, whether the evaluation process is reproducible, and whether the leaderboard can distinguish model capability, harness design, and changes in environment state.

## 0.5.2 Representative Work and Entry Points

- [DyVal](https://arxiv.org/abs/2309.17167): dynamically generates reasoning tasks to reduce fixed-question contamination; useful for observing the "generate new questions by rules" route.
- [LatestEval](https://arxiv.org/abs/2312.12343): builds reading-comprehension evaluations from the latest news and time-sensitive material; its core value is turning "has the model seen the question" into a time-slice issue.
- [DARG](https://arxiv.org/abs/2406.17271): dynamically evaluates LLM reasoning with an adaptive reasoning graph; the core idea is to generate follow-up questions based on a model's answer path, reducing the ability to game fixed prompt templates.
- [LiveBench](https://arxiv.org/abs/2406.19314) ([open-source code](https://github.com/LiveBench/LiveBench); [Leaderboard](https://livebench.ai/)): a comprehensive leaderboard that continuously releases new questions across math, coding, language, reasoning, data analysis, and instruction following. It is a representative entry point for "contamination-limited live benchmarks."
- [BenchmarkCards](https://arxiv.org/abs/2410.12974) ([open-source code](https://github.com/SokolAnn/BenchmarkCards)): a standardized benchmark documentation framework. When reading a new benchmark, it can be used to check whether task goals, data sources, metrics, limitations, risks, and applicability boundaries are clearly stated.
- [Statistical Uncertainty Quantification for Aggregate Performance Metrics](https://arxiv.org/abs/2501.04234): Studies uncertainty estimates for aggregated benchmark scores. Core idea: use bootstrap, hierarchical modeling, and task-weight visualization so benchmark summaries report ranking uncertainty instead of presenting one average as definitive.
- [Humanity's Last Exam](https://arxiv.org/abs/2501.14249) / [HLE-Rolling](https://agi.safe.ai/) (change log: [centerforaisafety/hle](https://github.com/centerforaisafety/hle/blob/main/hle-rolling-changes.txt)): HLE provides difficult expert questions, while HLE-Rolling reduces public-question contamination, errors, and saturation through continuous revision, new questions, and live submission.
- [LLM-Safety Evaluations Lack Robustness](https://arxiv.org/abs/2503.02574): Audits robustness in LLM safety evaluations. Core idea: test how safety-evaluation conclusions shift under perturbations or evaluation-design choices so benchmark scores are not treated as stable capability measurements without reliability checks.
- [Know Thy Judge](https://arxiv.org/abs/2503.04474): Meta-evaluates the robustness of LLM safety judges. Core idea: stress-test judge behavior under perturbations so safety benchmark scores do not silently inherit brittle or biased judge decisions.
- [Safer or Luckier?](https://arxiv.org/abs/2503.09347): Audits LLM safety evaluators under artifact sensitivity. Core idea: test whether safety-judge scores reflect robust risk assessment or are shifted by superficial dataset artifacts, making evaluator brittleness visible before benchmark results are trusted.
- [SPHERE](https://arxiv.org/abs/2504.07971): An evaluation-card framework for human-AI systems. Core idea: document system context, human roles, metrics, limitations, and deployment assumptions so human-AI evaluations are auditable rather than reduced to a single score.
- [The Leaderboard Illusion](https://arxiv.org/abs/2504.20879): Audits Chatbot Arena-style leaderboard reliability. Core idea: show how private testing, selective disclosure, sampling imbalance, and model removal policies can bias rankings, so leaderboard scores need protocol-level scrutiny.
- [SWE-rebench](https://arxiv.org/abs/2505.20411) ([Leaderboard](https://swe-rebench.com/leaderboard)): automatically collects and decontaminates SWE tasks, emphasizing fresh issues, interactive execution feedback, and a task-construction pipeline.
- [SWE-bench-Live](https://arxiv.org/abs/2505.23419) ([open-source code](https://github.com/SWE-bench-Live/SWE-bench-Live); [Leaderboard](https://swe-bench-live.github.io/)): continuously generates tasks from recent GitHub issues and PRs, with a focus on reducing memorization and overfitting risk in static software-engineering benchmarks.
- [Auto-Arena](https://aclanthology.org/2025.acl-long.223/): Automates LLM evaluation through agent peer battles and committee discussions. Core idea: make pairwise debate and multi-judge deliberation part of the evaluation protocol so model comparison is less dependent on one static prompt or one judge.
- [SWE-MERA](https://arxiv.org/abs/2507.11059): dynamic evaluation for software-engineering agents; the core idea is to continuously collect, execute, and verify new tasks, moving agentic SWE evaluation from a one-time snapshot to a rolling question set.
- [Multi-Agent-as-Judge](https://arxiv.org/abs/2507.21028): Aligns LLM-agent-based automated evaluation with multi-dimensional human evaluation. Core idea: use multiple judging agents and structured dimensions to reduce single-judge bias and make automated evaluation closer to human review.
- [ConfProBench](https://arxiv.org/abs/2508.04576): Evaluates step-level confidence reliability for MLLM-based process judges. Core idea: perturb reasoning steps with synonym, syntax, and image changes, then measure confidence robustness, sensitivity, and calibration rather than only correctness.
- [Beyond statistical significance](https://arxiv.org/abs/2509.22612): Quantifies uncertainty and statistical variability in multilingual and multitask NLP evaluation. Core idea: use resampling to estimate replication uncertainty for benchmark metrics, rankings, and pairwise model differences instead of treating leaderboard scores as fixed.
- [ProJudge](https://openaccess.thecvf.com/content/ICCV2025/html/Ai_ProJudge_A_Multi-Modal_Multi-Discipline_Benchmark_and_Instruction-Tuning_Dataset_for_MLLM-based_ICCV_2025_paper.html) ([project page](https://projudge.github.io/)): Evaluates MLLM-based process judges across multimodal disciplines. Core idea: make process-level judging itself a benchmark target so verifier and grader quality can be measured separately from base-task solving.
- [Detecting Silent Failures in Multi-Agentic AI Trajectories](https://arxiv.org/abs/2511.04032): Benchmarks anomaly detection over multi-agent trajectories. Core idea: curate labeled trajectory datasets for drift, cycles, and missing-detail failures so silent agent failures can be detected before final-output scoring hides them.
- [Hidden Measurement Error in LLM Pipelines](https://arxiv.org/abs/2604.11581): Audits variance hidden inside LLM-based annotation and evaluation pipelines. Core idea: treat judge choice, temperature, and prompt phrasing as measurement-error sources so benchmark conclusions include uncertainty beyond ordinary sampling intervals.
- [Yourbench](https://openreview.net/forum?id=bkWERVKzuP): Generates dynamic evaluation sets with LLMs. Core idea: let benchmark builders instantiate task-specific tests from private or fresh materials so static public test sets are not the only evaluation substrate.
- [Fluid Language Model Benchmarking](https://openreview.net/forum?id=mxcCg9YRqj): Studies benchmark fluidity for language-model evaluation. Core idea: treat evaluation sets as evolving objects and measure robustness of conclusions under controlled benchmark refresh and variation.
- [EvalAgents](https://openreview.net/forum?id=erGpkHCybv): Discovers implicit evaluation criteria from the web. Core idea: use web-derived criteria to make evaluation rubrics more task-adaptive and less dependent on hand-written generic score sheets.
- [AgentRewardBench](https://openreview.net/forum?id=fQcUZMPIvu): Evaluates automatic evaluations of web-agent trajectories. Core idea: test whether reward models and automatic judges can correctly score full agent trajectories, not just final answers or single screenshots.
- [Judge's Verdict](https://arxiv.org/abs/2510.09738): Analyzes LLM-as-judge capability through agreement with human judgments. Core idea: treat judge reliability itself as an evaluation target, exposing where automated verdicts align with or diverge from human assessment.
- [Auto-BenchmarkCard](https://arxiv.org/abs/2512.09577): automatically generates benchmark documentation cards; useful for quickly exposing missing descriptions of data, metrics, and limitations as the number of benchmarks grows rapidly.
- [RULERS](https://arxiv.org/abs/2601.08654): Provides locked rubrics and evidence-anchored scoring for robust LLM evaluation. Core idea: compile natural-language rubrics into executable criteria so judge behavior is less prompt-sensitive and more auditable.
- [Rubric-Conditioned LLM Grading](https://arxiv.org/abs/2601.08843): Studies rubric-conditioned automated grading under alignment, uncertainty, and robustness criteria. Core idea: make grading rubrics part of the evaluation object so judge reliability and uncertainty can be measured rather than assumed.
- [The Judge Who Never Admits](https://arxiv.org/abs/2602.07996): Audits hidden shortcuts in LLM-as-judge evaluation. Core idea: inject controlled metadata cues and compare verdict shift against cue acknowledgment, revealing when judges rely on irrelevant signals without admitting them in rationales.
- [SWE-rebench V2](https://arxiv.org/abs/2602.23866): a language-agnostic, larger-scale dynamic SWE task construction and execution evaluation; it extends the automated decontaminated collection route and expands executable tasks to more languages and repository ecosystems.
- [A Coin Flip for Safety](https://arxiv.org/abs/2603.06594): Audits LLM-as-judge reliability for adversarial robustness evaluation. Core idea: compare judge behavior against human-verified labels under red-team distribution shifts so safety scores do not inherit unstable evaluator bias.
- [CUBE](https://arxiv.org/abs/2603.15798): proposes a Common Unified Benchmark Environments protocol standard built on MCP and Gym; useful for reducing the integration tax across rapidly multiplying agent benchmarks and for separating task, benchmark, package, and registry concerns.
- [FACT-E](https://arxiv.org/abs/2604.10693): evaluates faithfulness of chain-of-thought reasoning through causal perturbation and step-to-step dependence checks; useful for separating coherent but unsupported traces from reasoning paths that actually support the answer.
- [Terminal Wrench](https://arxiv.org/abs/2604.17596) ([open-source code](https://github.com/few-sh/terminal-wrench)): evaluates whether terminal benchmarks can be bypassed through reward hacking; its core value is making environment vulnerabilities, scoring shortcuts, and trajectory manipulation explicit benchmark-reliability issues.
- [QuickScope](https://arxiv.org/abs/2604.17842): provides quick certification for hard questions in dynamic benchmarks; the core idea is to offer a lower-cost pre-screening mechanism for whether a question is truly difficult and discriminative.
- [How Sensitive Are Safety Benchmarks to Judge Configuration Choices?](https://arxiv.org/abs/2604.24074): Audits how LLM safety-benchmark scores shift under judge prompt and configuration choices. Core idea: treat the judge setup as an evaluation variable rather than an implementation detail, exposing score and ranking instability in safety benchmarks.
- [Claw-Eval-Live](https://arxiv.org/abs/2604.28139) ([project page](https://claw-eval-live.github.io/); [open-source code](https://github.com/Claw-Eval-Live/Claw-Eval-Live)): a live agent benchmark that changes with real workflow demand; its value is refreshing the task distribution quarterly while retaining mock services, workspace fixtures, traces, and graders for reproducibility.

## 0.5.3 Usage Advice

When reading a new benchmark, first check whether it explains data sources, sampling time, contamination controls, question refresh mechanisms, failed-sample audits, judge calibration, environment snapshots, and leaderboard submission protocols. For agent benchmarks, additionally check whether they preserve full trajectories, tool calls, environment state, cost, runtime, and multi-run variance; otherwise, leaderboard rankings can easily mix in harness engineering, environmental chance, and scoring shortcuts.
