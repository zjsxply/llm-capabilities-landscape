## 2.2.1 Leaderboard

- [SWE-bench Leaderboard](https://www.swebench.com/): The official entry point for SWE-bench, Lite, Verified, Multilingual, and related results; the core continuous leaderboard for repo-level issue resolving.
- [SWE-bench Multimodal Leaderboard](https://www.swebench.com/multimodal.html): The official leaderboard for visual/frontend issue statements and JavaScript software libraries, useful for observing whether agents generalize from text-based Python fixes to multimodal software tasks.
- [SWE-Lancer Diamond Leaderboard](https://swelancer.github.io/leaderboard/): OpenAI SWE-Lancer's public Diamond leaderboard, emphasizing realistic freelance-style software tasks and delivery evaluation closer to economic value.
- [SWE-rebench Leaderboard](https://swe-rebench.com/leaderboard): A continuous leaderboard for decontaminated, interactive SWE tasks, useful for observing generalization to fresh GitHub issues and use of execution feedback.
- [SWE-bench-Live Leaderboard](https://swe-bench-live.github.io/): A live leaderboard that continuously generates tasks from recent GitHub issues and PRs, focused on reducing the risk that static benchmarks are memorized or overfit.
- [SWE-MERA Leaderboard](https://mera-evaluation.github.io/demo-swe-mera/): A dynamic leaderboard that supports viewing results by task collection time window, useful for contamination-aware temporal-slice comparisons.
- [CodeClash Leaderboard](https://codeclash.ai/): A goal-oriented, multi-round tournament-style software-engineering leaderboard, suitable for evaluating long-term code maintenance, log analysis, and self-driven strategy improvement.
- [Holistic Agent Leaderboard](https://hal.cs.princeton.edu/): A cross-task agent leaderboard covering SWE-bench Verified, SWE-bench Multimodal, SWE-Lancer Diamond, and other tasks, useful for comparing the generality of different agent harnesses.
- [SWE-PolyBench Leaderboard](https://amazon-science.github.io/SWE-PolyBench/): A multilingual repository-level coding-agent leaderboard; its value is in providing data, containerized evaluation, and public rankings for non-Python code-agent evaluation.
- [Multi-SWE-Bench Leaderboard](https://multi-swe-bench.github.io/): A real multi-language issue-fixing leaderboard; here multilingual refers to programming languages, making it a public reference for evaluating multilingual coding agents.
- [Copilot Arena](https://gclef-cmu.org/research/2025copilotarena/): A code-model preference arena from real IDE usage; it complements SWE-bench-style offline test pass rates with developer preferences, interaction context, and in-the-wild usage signals.
- [Aider Polyglot Leaderboard](https://aider.chat/docs/leaderboards/): A practical multilingual code-editing leaderboard; while not a paper-style benchmark, its tasks and implementation are public and useful for quick comparison of multilingual code-editing ability.

## 2.2.2 Bench

- [SWE-Bench](https://arxiv.org/abs/2310.06770): What it evaluates: repository-level bug fixing based on real GitHub issues, by generating patches that pass tests. Core idea: define executable SWE evaluation with real repositories, reproducible environments, and test passing. ([code](https://github.com/SWE-bench/SWE-bench))
- [SciCode](https://arxiv.org/abs/2407.13168): What it evaluates: real coding tasks in scientific and research settings, curated by scientists. Core idea: tasks are closer to scientific problem decomposition and verifiable tests, emphasizing the combination of knowledge recall, reasoning, and code synthesis. ([code](https://github.com/scicode-bench/SciCode))
- [ContextBench](https://arxiv.org/abs/2602.05892): Evaluates context retrieval in coding agents. Core idea: isolate whether an agent can locate the files, symbols, and prior evidence needed for a code task before patch generation or reasoning begins.
- [GameDevBench](https://arxiv.org/abs/2602.11103): Evaluates agentic software-development capability through game development tasks. Core idea: test whether agents can plan, implement, debug, and deliver interactive game projects rather than only solve repository issues or isolated coding problems.
- [ReqElicitGym](https://arxiv.org/abs/2602.18306): Evaluates interview competence in conversational requirements elicitation. Core idea: provide an environment where agents must ask useful follow-up questions and uncover requirements rather than only implement a fully specified task.
- `SWE-Bench Verified`: What it evaluates: a more reliable and reproducible subset of SWE-Bench, emphasizing evaluability and environment stability. Core idea: reduce evaluation noise through stricter data and evaluation filtering. ([dataset](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified))
- [SWE-bench Multimodal](https://arxiv.org/abs/2410.03859): What it evaluates: issue resolving in visual/frontend JavaScript software libraries. Core idea: incorporate image-based issue statements, visual tests, and cross-language frontend repositories into the SWE-bench paradigm, using 617 tasks to test whether agents generalize from Python text bug fixing to the visual software domain. ([project page](https://www.swebench.com/multimodal.html))
- [SyncBench](https://arxiv.org/abs/2502.06994): What it evaluates: out-of-sync recovery in collaborative software engineering. Core idea: construct 24,332 executable scenarios from real GitHub collaboration evolution to test whether agents can resynchronize, communicate, and fix issues after environment state changes. ([project page](https://xhguo7.github.io/SyncMind/))
- [Copilot Arena](https://arxiv.org/abs/2502.09328) ([project page](https://gclef-cmu.org/research/2025copilotarena/), [code](https://github.com/lmarena/copilot-arena)): What it evaluates: code LLM preference and interaction quality in real development environments. Core idea: collect pairwise model comparisons and user preferences inside IDEs to complement "does the patch pass tests" with code-assistant experience, context use, and suggestion quality.
- [SWE-Lancer / SWE-Lancer Diamond](https://arxiv.org/abs/2502.12115): What it evaluates: end-to-end delivery capability for software tasks closer to real engineering collaboration and freelance work, from requirements to implementation and acceptance. Core idea: use task settings closer to real development workflows, emphasizing verifiable delivery and process execution; public leaderboards often track higher-value tasks through the Diamond split.
- [SWEE-Bench / SWA-Bench](https://arxiv.org/abs/2503.07701): What it evaluates: larger-scale repo-level issue resolving and applied software tasks automatically constructed by SetUpAgent. Core idea: automate historical dependency reconstruction, test execution, and result parsing to expand SWE-bench repository coverage and expose distribution differences.
- [Multi-SWE-Bench](https://arxiv.org/abs/2504.02605): What it evaluates: multilingual issue-resolving SWE tasks across repositories, dependencies, and toolchains in different languages. Core idea: reuse the SWE evaluation paradigm across multilingual repositories and release multilingual-compatible agent/harness revisions for reproducible evaluation, covering 1,632 instances in 7 languages. ([code](https://github.com/multi-swe-bench/multi-swe-bench))
- [R2E-Gym](https://arxiv.org/abs/2504.07164): What it evaluates: executable SWE-agent training/evaluation environments and test-time scaling. Core idea: use SYNGEN to synthesize issue-like tasks with execution environments from commits, and combine execution-based and execution-free verifiers to support open-weight SWE-agent training. ([project page](https://r2e-gym.github.io/), [code](https://github.com/R2E-Gym/R2E-Gym))
- [SWE-PolyBench](https://arxiv.org/abs/2504.08703): What it evaluates: multilingual repo-level SWE evaluation and comparison. Core idea: a more evaluation-harness-oriented platform that places SWE tasks from different language ecosystems into a unified comparison protocol. ([code](https://github.com/amazon-science/SWE-PolyBench))
- [WebGen-Bench](https://arxiv.org/abs/2505.03733) ([code](https://github.com/mnluzimu/WebGen-Bench), [dataset](https://huggingface.co/datasets/luzimu/WebGen-Bench)): What it evaluates: LLM agents generating multi-file interactive websites from scratch. Core idea: pair website-generation instructions with manually refined browser-executable functionality tests, so frontend code generation is judged by user-visible behavior rather than only code similarity.
- [EffiBench-X](https://arxiv.org/abs/2505.13004) ([code](https://github.com/EffiBench/EffiBench-X), [dataset](https://huggingface.co/datasets/EffiBench/effibench-x)): What it evaluates: efficiency of LLM-generated code across Python, C++, Java, JavaScript, Ruby, and Go. Core idea: keep functional correctness as a gate but compare runtime against human-expert solutions, exposing whether generated code is merely correct or practically efficient.
- [CodeSimpleQA](https://arxiv.org/abs/2505.15843): What it evaluates: basic code understanding and question answering. Core idea: use clearer, judgeable QA forms to complement SWE with a characterization of code knowledge and understanding.
- [SWE-rebench](https://arxiv.org/abs/2505.20411): What it evaluates: decontaminated, interactive repository-level SWE evaluation. Core idea: control training contamination and environment bias in SWE-bench-style issue resolving, while allowing agents to complete fixes through interactive execution feedback.
- [SWE-bench-Live](https://arxiv.org/abs/2505.23419): What it evaluates: continuously updated real GitHub issue resolving. Core idea: construct live tasks from recent issues and pull requests so evaluation refreshes over time, reducing the risk of overfitting or leakage in static benchmarks. ([code](https://github.com/SWE-bench-Live/SWE-bench-Live))
- [GSO](https://arxiv.org/abs/2505.23671): What it evaluates: performance-optimization tasks in real repositories. Core idea: construct cross-language optimization tasks from commit history, using performance tests and expert optimizations as references to test whether SWE agents can locate bottlenecks and deliver effective speedups. ([project page](https://gso-bench.github.io/), [code](https://github.com/gso-bench/gso))
- [CodeAssistBench](https://papers.nips.cc/paper_files/paper/2025/hash/ba9d95c583a154bb77b5f5900691430e-Abstract-Datasets_and_Benchmarks_Track.html) ([code](https://github.com/amazon-science/CodeAssistBench)): What it evaluates: multi-turn chat-based code assistance. Core idea: use containerized real repositories, simulated users, and real issues to measure how helpful a code assistant is in multi-turn Q&A, context tracking, and codebase understanding, rather than only one-shot patch generation.
- [SWE-bench Multilingual](https://www.swebench.com/multilingual): What it evaluates: SWE-bench-style issue resolving on multilingual codebases. Core idea: reuse SWE-bench data and evaluation infrastructure as much as possible, incorporating multilingual capability as an evaluation-layer extension in the same harness, with 300 tasks across 9 languages. ([dataset](https://huggingface.co/datasets/SWE-bench/SWE-bench_Multilingual), [code](https://github.com/SWE-bench/SWE-bench))
- [SWE-Evo](https://arxiv.org/abs/2506.13339): What it evaluates: self-evolving or self-rewriting solving and generalization for SWE tasks. Core idea: characterize test-time evolutionary agent behavior through an iterative rewriting and self-improvement protocol.
- [SWE-Bench-CL](https://arxiv.org/abs/2507.00014): What it evaluates: continual-learning-style SWE tasks organized by repository evolution timelines. Core idea: reorder SWE-Bench Verified issues into natural issue sequences, directly evaluating whether agents can accumulate experience, transfer knowledge, and avoid forgetting. ([code](https://github.com/thomasjoshi/agents-never-forget))
- [SWE-MERA](https://arxiv.org/abs/2507.11059): What it evaluates: dynamically collected, continuously updated real GitHub issue resolving. Core idea: reduce contamination risk through automated filtering, LLM quality validation, and time-windowed leaderboards, while supporting observation of agent generalization by task period. ([Leaderboard](https://mera-evaluation.github.io/demo-swe-mera/), [dataset](https://huggingface.co/datasets/MERA-evaluation/SWE-MERA))
- [AlgoTune](https://arxiv.org/abs/2507.15887): What it evaluates: numerical algorithms and code performance optimization. Core idea: require agents to maintain correctness and improve speed under executable feedback, complementing SWE bug fixing with algorithm engineering, performance diagnosis, and optimization search.
- [GitTaskBench](https://arxiv.org/abs/2508.18993): What it evaluates: real repo-level code-agent tasks, including repository understanding, environment setup, incremental development/fixing, and delivery. Core idea: measure the "real engineering loop" of code agents with more end-to-end repository task chains and include cost/efficiency dimensions. ([code](https://github.com/QuantaAlpha/GitTaskBench))
- [SWE-Bench Pro](https://arxiv.org/abs/2509.16941): What it evaluates: a harder SWE task set closer to "engineering-grade agent" needs. Core idea: raise task complexity and process requirements to better separate strong agents.
- [FeatBench](https://arxiv.org/abs/2509.22237): What it evaluates: repository-level feature implementation from natural-language requirements only. Core idea: provide no code hints and use a continuously updated pipeline to reduce contamination, focusing on requirement understanding, scope control, and regression risk. ([code](https://github.com/TsinghuaISE/FeatBench))
- [TF-Bench](https://arxiv.org/abs/2509.23686): What it evaluates: program-semantics reasoning through System F type inference. Core idea: use a formal deductive programming-language task to test semantic reasoning beyond token associations or unit-test shortcuts.
- [ArtifactsBench](https://arxiv.org/abs/2510.04316): What it evaluates: software-task completion oriented toward deliverable artifacts. Core idea: constrain outputs to verifiable engineering artifacts and workflow results rather than a single code snippet.
- [Holistic Agent Leaderboard (HAL)](https://arxiv.org/abs/2510.11977) ([code](https://github.com/princeton-pli/hal-harness)): What it evaluates: unified cross-benchmark agent evaluation covering SWE-bench Verified, SWE-bench Multimodal, SWE-Lancer Diamond, and other software-engineering tasks. Core idea: standardize task execution, cost, time, trajectories, and leaderboard submission flow to compare the generality of different software-agent harnesses.
- [Paper2Web](https://arxiv.org/abs/2510.15842): What it evaluates: generating interactive academic project websites from research papers. Core idea: add paper-conditioned webpage-generation tasks, layout and interactivity metrics, and PaperQuiz-style knowledge-retention checks beyond generic frontend instructions.
- [ImpossibleBench](https://arxiv.org/abs/2510.20270): What it evaluates: LLM agents' propensity to exploit test cases. Core idea: create impossible variants of coding tasks from benchmarks such as LiveCodeBench and SWE-bench to diagnose specification gaming, where passing tests need not mean solving the intended task.
- [CodeClash](https://arxiv.org/abs/2511.00839): What it evaluates: open-goal software-engineering tournaments. Core idea: have agents autonomously modify repositories, read logs, write tests, and compete against opponents across multiple tournament rounds, measuring long-term code maintenance and strategic improvement capability. ([project page](https://codeclash.ai/), [code](https://github.com/CodeClash-ai/CodeClash))
- [SWE-Sharp-Bench](https://arxiv.org/abs/2511.02352): What it evaluates: repo-level bug fixing in the C# / .NET ecosystem. Core idea: extend SWE-bench-style issue resolving to a strongly typed, enterprise-language ecosystem with complex build flows, validating patches with real tests.
- [SWE-Bench++](https://arxiv.org/abs/2512.17419): What it evaluates: automatically generated SWE benchmarks and high-quality executable instances. Core idea: explicitly include environment synthesis, patch generation, and validation filtering in task generation to reduce manual construction bottlenecks. ([code](https://github.com/TuringEnterprises/SWE-Bench-plus-plus))
- [WebCoderBench](https://arxiv.org/abs/2601.02430): What it evaluates: web application generation from real user requirements. Core idea: use 1,572 realistic requirements and 24 interpretable metrics across 9 perspectives to evaluate generated web apps without depending only on reference implementations or test cases.
- [RepoReason](https://arxiv.org/abs/2601.03731): What it evaluates: repository-level agentic code reasoning. Core idea: use execution-driven mutations and abductive assertion verification to test whether agents reason over codebase behavior, not only patch known issues.
- [OctoBench](https://arxiv.org/abs/2601.10343): What it evaluates: scaffold-aware instruction following in repository-grounded coding. Core idea: require agents to respect persistent constraints and scaffold instructions across full trajectories with objective checklist scoring.
- [Terminal-Bench 2.0](https://arxiv.org/abs/2601.11868): What it evaluates: end-to-end task completion in terminal environments, including reading/writing files, running commands, fixing issues, and producing executable results. Core idea: ground "programming" in real CLI operational loops, evaluating executability rather than pure code snippets. ([Registry](https://www.tbench.ai/registry/terminal-bench/2.0), [code](https://github.com/harbor-framework/terminal-bench))
- [IDE-Bench](https://arxiv.org/abs/2601.20886): What it evaluates: LLMs as IDE agents on real software engineering tasks. Core idea: run agents through IDE-native tool interfaces over unpublished repositories, covering feature implementation, bug fixing, refactoring, and performance optimization.
- [FeatureBench](https://arxiv.org/abs/2602.10975): What it evaluates: complex feature development by agentic coding systems. Core idea: test end-to-end feature implementation with executable validation; keep it distinct from the earlier FeatBench entry because the title and release are separate.
- [RepoMod-Bench](https://arxiv.org/abs/2602.22518) ([code](https://github.com/Modelcode-ai/mcode-benchmark)): What it evaluates: repo-level code modernization and cross-language migration. Core idea: evaluate functional equivalence with implementation-agnostic tests.
- [Rust-SWE-bench](https://arxiv.org/abs/2602.22764): What it evaluates: repo-level issue resolving in the Rust ecosystem. Core idea: incorporate ownership, lifetimes, Cargo builds, and test constraints into SWE-bench-style evaluation, highlighting the impact of strong type systems and toolchains on coding agents.
- [SWE-rebench V2](https://arxiv.org/abs/2602.23866): What it evaluates: language-agnostic, larger-scale dynamic SWE task construction and execution evaluation. Core idea: extend SWE-rebench's decontaminated automated collection path to more languages and repository ecosystems.
- [SWE-CI](https://arxiv.org/abs/2603.03823): What it evaluates: software repair and regression validation driven by CI signals. Core idea: incorporate continuous-integration failures, log localization, patch generation, and rerun validation into one task protocol, filling gaps in SWE evaluation that only uses local tests.
- [WebVR](https://arxiv.org/abs/2603.13391): What it evaluates: webpage recreation from interaction videos. Core idea: use demonstration videos and human-aligned visual rubrics to test whether multimodal models can recover page layout, interaction flow, and motion cues for web generation.
- [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401): What it evaluates: the marginal benefit of skill injection on real SWE tasks. Core idea: build executable, deterministically verifiable paired comparisons with and without skills to isolate the true contribution of skills. ([code](https://github.com/GeniusHTX/SWE-Skills-Bench))
- [VIBEPASS](https://arxiv.org/abs/2603.15921): What it evaluates: debugging and repair loops in vibe-coding-style agents. Core idea: jointly test fault-triggering test generation and fault-targeted repair instead of judging patch generation alone.
- [VIBE-Pro](https://benchlm.ai/benchmarks/vibePro) (reported in the [MiniMax M2.7 model report](https://www.minimax.io/news/minimax-m27-en)): What it evaluates: repo-level full-project delivery in vibe-coding scenarios. Core idea: judge whether an agent can turn broad requirements into complete working projects across web, mobile, and simulation-style implementation tasks, complementing issue-fixing benchmarks such as SWE-Bench Pro and repo-construction benchmarks such as NL2Repo-Bench.
- [SLUMP](https://arxiv.org/abs/2603.17104): What it evaluates: faithfulness loss in long-horizon coding agents. Core idea: reveal requirements progressively and score whether later code preserves emergent specifications across components.
- [Aider Polyglot](https://github.com/Aider-AI/polyglot-benchmark): What it evaluates: comparison and scoring for cross-language programming/modification tasks. Core idea: measure real cross-language code-editing ability with multilingual samples and unified scoring rules.
- [RACE-bench](https://arxiv.org/abs/2603.26337): What it evaluates: repo-level feature addition and intermediate reasoning. Core idea: evaluate issue understanding, localization, and implementation decomposition in addition to patch correctness.
- [SWE-Chain](https://arxiv.org/abs/2605.14415): What it evaluates: repo-level software maintenance under chained release upgrades. Core idea: turn version migration into a sequence of continuous tasks and evaluate linked fixes across versions.

## 2.2.3 Agent Harness

- [AutoCodeRover](https://arxiv.org/abs/2404.05427) ([code](https://github.com/AutoCodeRoverSG/auto-code-rover)) combines structured code search, AST-level localization, and test feedback for GitHub issue fixing; design keywords: program-structure retrieval, fault localization, low-cost patch generation.
- [SWE-agent](https://arxiv.org/abs/2405.15793) ([code](https://github.com/SWE-agent/SWE-agent)) is a standard baseline for in-repository loop-based repair.
- [MASAI](https://arxiv.org/abs/2406.11638) ([code](https://github.com/masai-dev-agent/masai)) decomposes SWE tasks into multiple goal-specific subagents for localization, information gathering, editing, and verification; design keywords: modular subagents, shorter trajectories, SWE-bench Lite.
- [Agentless](https://arxiv.org/abs/2407.01489) ([code](https://github.com/OpenAutoCoder/Agentless)) represents the workflow route of `localization -> repair -> validation`.
- [OpenHands](https://arxiv.org/abs/2407.16741) ([code](https://github.com/OpenHands/OpenHands)) is closer to a general software-development agent platform.
- [DEI / SWE-Comm](https://arxiv.org/abs/2408.07060) ([code](https://github.com/SalesforceAIResearch/swecomm)) combines multiple open-source SWE agents into a committee, selecting and fusing different agents' strengths by task; design keywords: multi-agent ensemble, complementary expertise, SWE-bench Lite.
- [RepoGraph](https://arxiv.org/abs/2410.14684) ([code](https://github.com/ozyyshr/RepoGraph)): Enhances localization and repair context organization with structured repository graphs.
- [SWE-Search](https://arxiv.org/abs/2410.20285) ([code](https://github.com/a-antoniades/swe-search)): Explicitly models repository repair as a search process, emphasizing backtrackable candidate exploration.
- [OrcaLoca](https://arxiv.org/abs/2502.00350) ([code](https://github.com/fishmingyu/OrcaLoca)): A specialized agent framework for software issue localization; core idea: combine decomposed localization actions, relevance scoring, and context trimming into a more stable repository-navigation loop.
- [SyncMind](https://arxiv.org/abs/2502.06994) ([code](https://github.com/xhguo7/SyncMind)): An out-of-sync recovery framework for collaborative software engineering; core idea: explicitly model state drift, collaboration communication, and resource constraints to evaluate recovery after shared-codebase changes.
- [debug-gym](https://arxiv.org/abs/2503.21557) ([code](https://github.com/microsoft/debug-gym)): A text-based interactive debugging environment; core idea: package pdb, execution feedback, and code-exploration tools as an agent environment for evaluating and training information-gathering debugging behavior.
- [Satori-SWE](https://arxiv.org/abs/2505.23604) ([code](https://github.com/satori-reasoning/Satori-SWE)): A test-time scaling route for SWE, emphasizing allocation of reasoning budget and search depth.
- [iReDev](https://arxiv.org/abs/2507.13081): A knowledge-driven multi-agent framework for requirements development. Core idea: coordinate specialized agents around domain knowledge, requirement refinement, and consistency checking so software requirements can be elicited and improved as an explicit analyst workflow.
- mini-SWE-agent ([code](https://github.com/SWE-agent/mini-swe-agent); no independent paper; a lightweight terminal repair harness maintained by the SWE-agent team; design keywords: small core, command-line execution, SWE-bench adaptation)
- SWE-ReX ([code](https://github.com/SWE-agent/SWE-ReX); no independent paper; a remote execution and environment-management layer maintained by the SWE-agent team; design keywords: execution isolation, batch runs, SWE-bench/CodeClash reuse)
- sb-cli ([code](https://github.com/SWE-bench/sb-cli); no independent paper; the official SWE-bench CLI for submission, run management, and report retrieval; design keywords: official evaluation API, prediction submission, report reproduction)
- [Prometheus](https://arxiv.org/abs/2507.19942) ([code](https://github.com/EuniAI/Prometheus); an engineering-oriented repair agent for SWE-bench; design keywords: engineered pipeline, stable execution)
- [TRAE Agent](https://arxiv.org/abs/2507.23370) ([code](https://github.com/bytedance/trae-agent); a ByteDance repository-level repair agent; design keywords: test-time scaling, repository-level analysis)
- [SE-Agent](https://arxiv.org/abs/2508.02085) ([code](https://github.com/JARVIS-Xs/SE-Agent)): A trajectory-level self-evolving software-engineering agent; core idea: use revision, recombination, and refinement to exchange information among historical trajectories and improve multi-step repair quality.
- [The Complexity Trap](https://arxiv.org/abs/2508.21433) ([code](https://github.com/JetBrains-Research/the-complexity-trap); a systematic comparison of observation masking and LLM summarization for context-management cost and performance on SWE-agent and SWE-bench Verified; design keywords: context management, cost control, harness simplification)
- [Holistic Agent Leaderboard](https://arxiv.org/abs/2510.11977) ([code](https://github.com/princeton-pli/hal-harness); a cross-benchmark agent evaluation harness connecting SWE-bench Verified, SWE-bench Multimodal, SWE-Lancer Diamond, USACO, and other tasks to one submission and reproduction protocol; design keywords: unified agent interface, cross-task evaluation, public leaderboard)
- [CodeClash](https://arxiv.org/abs/2511.00839) ([code](https://github.com/CodeClash-ai/CodeClash); a goal-oriented software-engineering tournament harness based on the mini-SWE-agent interface, where agents continuously modify code, read logs, write tests, and compete against opponent repositories; design keywords: multi-round tournament, open goals, long-term maintenance)
- [OpenHands Software Agent SDK](https://arxiv.org/abs/2511.03690) ([code](https://github.com/OpenHands/OpenHands); composable and extensible SDK design for production agents, emphasizing execution isolation, lifecycle control, and tool/memory extension points; design keywords: SDK-style harness, composable interfaces, execution safety)
- [live-SWE-agent](https://arxiv.org/abs/2511.13646) ([code](https://github.com/OpenAutoCoder/live-swe-agent); a runtime self-evolving SWE agent; reports a 45.8% resolve rate with Claude 4.5 Sonnet on the SWE-Bench Pro public set, above SWE-agent's 43.6% under the same setting; design keywords: online self-evolution, per-task dynamic tool creation)
- MSWE-agent ([code](https://github.com/multi-swe-bench/MSWE-agent); no independent paper; a Multi-SWE-Bench-compatible version based on SWE-agent that adapts repository analysis, execution, and evaluation flows for multilingual projects; design keywords: multilingual compatibility, SWE-agent revision)
- MopenHands ([code](https://github.com/multi-swe-bench/MopenHands); no independent paper; a Multi-SWE-Bench-compatible version based on OpenHands, more focused on platform-level multilingual harness adaptation; design keywords: platform compatibility, multilingual execution)
- MagentLess ([code](https://github.com/multi-swe-bench/MagentLess); no independent paper; a Multi-SWE-Bench-compatible version based on Agentless that preserves the `localization -> repair -> validation` workflow while adapting to multilingual repositories; design keywords: lightweight workflow, multilingual issue resolving)
- [Confucius Code Agent](https://arxiv.org/abs/2512.10398) ([code](https://github.com/facebookresearch/cca-swebench); an industrial-grade long-horizon SWE agent; main evaluation is on the SWE-Bench Pro public set, reporting 59.0% Pass@1 with GPT-5.2 and 52.7% with Claude 4.5 Sonnet; design keywords: long-context management, persistent notes, meta-agent iteration)
- [Agentic Rubrics](https://arxiv.org/abs/2601.04171) (code: no stable public repository found; a contextual verifier workflow for SWE agents; design keywords: repository-interacting checklists, patch verification, task-specific rubrics)
- [SWE-Pruner](https://arxiv.org/abs/2601.16746) ([code](https://github.com/Ayanami1314/swe-pruner); a context-pruning module; design keywords: context pruning, key-information filtering)
- [SWE-Replay](https://arxiv.org/abs/2601.22129) (code: no stable public repository found; a test-time scaling method for modern SWE agents; on SWE-Bench Pro with mini-SWE-agent and Devstral-Small-2, improves from 28.73% to 28.97% while reporting a 3.1% average cost reduction; design keywords: trajectory reuse, forked replay, low-cost scaling)
- Harbor ([code](https://github.com/harbor-framework/harbor); no independent paper; the general agent-integration and trajectory-running harness for Terminal-Bench 2.0; design keywords: terminal tasks, agent adaptation, reproducible experiments)
- [Agyn](https://arxiv.org/abs/2602.01465) ([code](https://github.com/agynio/platform); an agent platform for real engineering tasks; design keywords: platform orchestration, real engineering-task hosting)
- [SWE-World](https://arxiv.org/abs/2602.03419) ([code](https://github.com/RUCAIBox/SWE-World); a Docker-free SWE training and evaluation substrate; design keywords: learned surrogate, execution-feedback replacement, low-cost evaluation)
